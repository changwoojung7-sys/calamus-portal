# 18. 인증 연동(LDAP·AD·SSO·MFA), 2D 업무 모드, 캘린더 연동 개념 정리

- 작성일: 2026-10-12 · 제품 기준 1.0.7
- 목적: 앞으로 개발할 기능의 **개념과 구현 방식**을 잊지 않도록 쉽게 정리한다.
- 결정 사항(2026-10-12)
  - **팀·전사 일정 관리 + 벽 일정 보드를 먼저 구현한다.**
  - 2D 업무 모드는 더 검토한다.
  - MFA는 LDAP/AD·SSO를 구현하면 우선순위를 낮춘다(3.5절 참고).

---

## 1. 지금 WorkNexus 로그인의 한계

직원 계정이 **WorkNexus 안에만** 따로 있다(이메일 + 비밀번호).

- 직원은 회사 메일 비밀번호와 별개로 비밀번호를 하나 더 외워야 한다.
- 퇴사자가 생기면 회사 계정을 막은 뒤 WorkNexus에서도 **따로** 막아야 한다. 잊으면 퇴사자가 계속 들어올 수 있다.
- 보안팀은 "비밀번호 하나만 알면 들어오는가"를 묻는다.

## 2. 세 가지 개념 한눈에

| 이름 | 한 줄 설명 | 비유 |
|---|---|---|
| **LDAP / AD** | 회사가 이미 가진 **직원 명부 서버**에 아이디·비밀번호를 대신 물어본다 | 우리 건물 경비실이 출입증을 따로 만들지 않고, 본사 인사팀 명부에 "이 사람 직원 맞아요?"라고 확인 |
| **SSO** | 회사 로그인 화면에서 **한 번 로그인**하면 WorkNexus도 바로 들어온다 | 회사 정문에서 사원증을 한 번 찍으면 안의 사무실 문이 그냥 열림 |
| **MFA** | 비밀번호에 **두 번째 확인**(휴대폰 인증 앱의 6자리 숫자 등)을 더한다 | 열쇠 + 지문 |

- **LDAP**: 직원 명부 서버와 대화하는 표준 "언어"(프로토콜) 이름이다.
- **AD(Active Directory)**: Windows를 쓰는 회사가 가장 많이 쓰는 직원 명부 서버 제품이다. AD는 LDAP으로 대화할 수 있다. 그래서 "LDAP/AD 연동"이라고 묶어 부른다.
- **SSO**는 방식(경험)의 이름이고, 실제 표준은 **OIDC**(최신·간단)와 **SAML**(오래된 대기업·공공에서 많이 씀) 두 가지다.

### 고객별로 필요한 것

| 고객 | 필요한 것 |
|---|---|
| 별도 로그인 시스템이 없는 중소기업 | (현재 방식) + MFA |
| Microsoft 365·Google Workspace를 쓰는 회사 | **SSO(OIDC)** — MFA는 회사 쪽이 처리 |
| 사내망 중심 제조업·연구소(Windows AD) | **LDAP/AD 연동** |
| 대기업·공공 | SAML SSO까지 요구할 수 있음 |

## 3. 실제로 어떻게 구현하는가

### 3.1 LDAP / AD 연동

**고객 IT 담당자가 알려 주는 것 (설정값 4개)**

| 값 | 예 | 뜻 |
|---|---|---|
| 서버 주소 | `ldaps://dc01.company.local:636` | 회사 AD 서버. `ldaps`는 암호화된 연결 |
| 조회용 계정 | `svc-worknexus` / 비밀번호 | 직원 목록을 **읽기만** 하는 전용 계정 |
| 검색 위치(Base DN) | `OU=직원,DC=company,DC=local` | AD 안에서 직원들이 들어 있는 폴더 |
| 허용 그룹(선택) | `WorkNexus사용자` | 이 그룹에 속한 사람만 로그인 허용 |

**동작 순서**

```text
1. 직원이 WorkNexus 로그인 화면에 회사 아이디·비밀번호 입력
2. WorkNexus 서버 → 회사 AD 서버에 "이 아이디·비밀번호 맞나요?" 질문 (bind)
3. AD가 "맞다"고 하면 → 이름·이메일·부서를 읽어 와 WorkNexus 사원과 연결(이메일 기준)
4. WorkNexus 로그인 완료. WorkNexus DB에는 비밀번호를 저장하지 않는다
```

- **조직도 동기화**: 매일 밤 AD의 허용 그룹을 읽어, 새 직원은 자동 등록하고 AD에서 비활성화된 사람(퇴사자)은 WorkNexus에서도 자동으로 막는다.
- **관리자 화면**: 관리자 센터에 "외부 인증 설정" 화면을 두고 위 4개 값을 입력한다. **연결 시험** 버튼으로 바로 확인한다.
- **사용 기술**: Node.js의 LDAP 라이브러리(예: `ldapts`). 서버 쪽 코드만 추가된다.
- **폐쇄망**: 회사 내부망 안에서 동작하므로 폐쇄망 고객에게 잘 맞는다.

### 3.2 SSO (OIDC 방식)

**고객 IT 담당자가 하는 일**

1. 회사 로그인 시스템(Microsoft Entra ID, Google Workspace, Keycloak 등)에 **WorkNexus를 앱으로 등록**한다.
2. 등록할 때 "돌아올 주소"로 `https://회사약칭.calamus.ai.kr/api/auth/oidc/callback`을 넣는다.
3. 등록이 끝나면 회사 로그인 시스템이 **값 3개**를 준다: 발급자 주소(Issuer), 클라이언트 ID, 클라이언트 비밀값(Secret).
4. 이 3개를 WorkNexus 관리자 센터 "외부 인증 설정"에 입력한다.

**동작 순서**

```text
1. 직원이 WorkNexus에서 [회사 계정으로 로그인] 클릭
2. 브라우저가 회사 로그인 화면(예: Microsoft 로그인)으로 이동
   → 직원이 로그인(회사 정책에 따라 MFA도 여기서 처리)
3. 회사 로그인 시스템이 "이 사람은 hong@company.com 입니다"라는 전자서명된 확인증(ID 토큰)을 들려서 WorkNexus로 돌려보냄
4. WorkNexus 서버가 서명이 진짜인지 확인 → 이메일로 사원을 찾아 로그인 완료
```

- WorkNexus는 직원 비밀번호를 **아예 보지 않는다.**
- 퇴사자의 회사 계정을 끄면 3단계가 실패하므로 WorkNexus에도 못 들어온다.
- **사용 기술**: Node.js의 OIDC 라이브러리(예: `openid-client`).
- **폐쇄망 주의**: Microsoft·Google 로그인은 인터넷이 필요하다. 폐쇄망 고객은 사내 로그인 서버(Keycloak, ADFS 등)를 쓴다.

### 3.3 두 방식 공통으로 정할 것

| 항목 | 권장 |
|---|---|
| 사원 연결 기준 | 이메일(또는 사번) |
| 처음 로그인한 사람 | 관리자가 미리 등록한 사람만 허용(기본) / 자동 등록(선택) |
| 관리자 권한 | 회사 그룹(예: `WorkNexus관리자`)에 속하면 관리자 |
| **비상용 관리자 계정** | 외부 인증이 고장 나도 들어올 수 있게 WorkNexus 자체 관리자 계정 1개는 **항상 유지** |
| 외부 인증 고장 시 | 일반 직원 로그인 실패 안내 + 관리자 비상 로그인 |

### 3.4 고객 없이 어떻게 시험하나

이 PC의 **WSL2 Docker**(Linux 빌드용으로 설치함)에서 시험용 인증 서버를 띄운다. 실제 고객 환경 없이도 끝까지 시험할 수 있다.

| 시험 대상 | 방법 |
|---|---|
| AD / LDAP | Docker로 Samba AD 또는 OpenLDAP 서버를 띄우고 시험 직원·그룹을 만든다 |
| SSO(OIDC) | Docker로 Keycloak을 띄워 앱 등록부터 로그인까지 시험한다 |
| Microsoft·Google | 무료 개발자 계정으로 실제 연동을 한 번 확인한다 |

### 3.5 개발 규모(대략)와 MFA 판단

| 항목 | 대략 기간 | 비고 |
|---|---|---|
| OIDC SSO | 1~1.5주 | Microsoft·Google·Keycloak을 한 번에 지원 |
| LDAP/AD 로그인 + 야간 동기화 | 1~1.5주 | 연결 시험 화면 포함 |
| SAML | +1주 | 고객 요구가 있을 때 |
| 자체 MFA(인증 앱 6자리) | 3~5일 | 아래 참고 |

- **MFA 판단(2026-10-12)**: LDAP/AD·SSO를 쓰는 고객은 회사 쪽에서 MFA를 처리하므로 WorkNexus 자체 MFA가 필요 없다. 다만 **AD나 회사 로그인 시스템이 없는 소규모 고객**은 계속 WorkNexus 비밀번호로만 로그인하므로, 그런 고객이 많아지면 자체 MFA를 다시 검토한다.

## 4. 2D 업무 모드 (2026-10-12 구현, 1.0.8 예정)

지금 포털(대시보드)은 공지·출근 확인·"오피스 입장" 정도라 **채팅·통화·회의를 쓰려면 반드시 3D에 들어가야** 한다. 저사양 PC·모바일·"회의만 하려는 사람"에게 큰 불편이다.

**구상**: 3D 화면을 아예 불러오지 않는 **업무 모드**.

| 영역 | 내용 |
|---|---|
| 동료 | 접속·근무 상태 목록 → 채팅 / 1:1 통화 / 화면공유 |
| 회의실 | 방 목록과 "지금 회의 중(n명)" → 바로 참여 |
| 일정 | 오늘 내 회의·팀 일정, 임박 알림에서 바로 참여 |
| 기타 | 근무 상태, 공지·게시판, 반응(손들기 등) |
| 전환 | 버튼 하나로 3D 오피스와 전환. 사용자별 기본 모드, 관리자는 회사 기본값 |

- **방 격리 원칙 유지**: 2D에서 회의에 참여하면 서버는 그 사람을 "그 방에 있는" 것으로 처리한다.
- **근처 대화**(거리 기반 음성)는 위치가 없으므로 2D에서는 쓰지 않는다.
- 채팅 창·통화·화면공유 보기·회의 창은 기존 화면을 재사용한다. 새로 만들 것은 목록 화면과 3D 없이 방에 들어가는 처리다.

**구현 결과(2026-10-12)**
- 2D는 대시보드 같은 "다른 화면"이 아니라 **오피스 안의 보기 방식**(`officeView: '3d' | '2d'`)으로 만들었다. 오피스를 떠나지 않으므로 회의·통화·공유를 정리하는 코드가 돌지 않는다.
- 회의 창·1:1 통화·채팅·근태·설정 등을 3D HUD에서 빼서 **공용 창 영역**(`SharedOverlayLayer`)으로 옮겼다. 3D↔2D를 바꿔도 이 창들은 닫히지 않는다(시험: 전환 중 회의 토큰 재발급 0회, 통화 유지).
- 2D에서는 3D 월드(WebGL)를 아예 띄우지 않고, 근처 대화를 끈다(서버도 2D 사용자의 근처 대화 토큰 거부). 동료 화면에는 💻 2D 표시.
- 같은 작업에서 **회의 창 분리**도 고쳤다: Chrome·Edge는 문서 PiP로 회의 창을 옮겨 연결을 유지하고, 그 밖의 브라우저는 팝업에서 내 공유가 보이고 중지할 수 있다.
- 남은 것: 관리자가 회사 기본 보기 방식을 정하는 설정.

## 5. 캘린더 연동 — 세 가지 방향

| 방식 | 동작 | 장점 | 주의 |
|---|---|---|---|
| **A. 내보내기**(WorkNexus → 구글·아웃룩) | 일정을 초대 파일(`.ics`)로 받아 개인 캘린더에 추가 | 가장 쉬움. 구글 설정 불필요. 폐쇄망에서도 됨 | 한 방향. 바뀌면 다시 받아야 함 |
| **B. 구글 일정 가져오기**(읽기 전용) | 구글 캘린더의 "비공개 iCal 주소"를 관리자가 붙여 넣으면 서버가 주기적으로 읽어 표시 | "구글에 입력해 두면 보이는" 방식 | 서버가 인터넷(구글)에 접속해야 함 → 폐쇄망 불가. 주소 유출 주의 |
| **C. 양방향 동기화** | 구글 계정 연결(OAuth) 후 서로 수정 반영 | 가장 편리 | 개발이 크고, 회사 일정이 구글로 나간다 → 보안 고객 설명과 충돌 |

**결정한 방향**: WorkNexus **자체 팀·전사 일정**을 중심에 두고(폐쇄망에서도 동작), 벽에 거는 **일정 보드**로 보여 준다. 구글은 **A(내보내기)까지만** 한다.

**구현 결과(2026-10-12, 1.0.8 예정)**
- 팀·전사 일정 달력(상단 📅 일정, 포털 이번 주 일정 카드), 벽 일정 보드(`schedule_board`)
- A안 두 가지: **구글 캘린더에 추가**(구글 새 일정 화면을 내용이 채워진 채 열고 사용자가 저장) + **파일로 받기(.ics)**(아웃룩·아이폰)
- 회의 예약·타운홀은 기존 API로 읽기만 하며 그 로직은 바꾸지 않았다. 자세한 내용은 `CHANGELOG_01.md` 2026-10-12 항목
