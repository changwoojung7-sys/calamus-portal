## 1. 제안 요약

WorkNexus를 단순한 **메타버스 가상오피스**로 판매하면 Microsoft Teams, Zoom, Gather 계열 제품과 직접 비교되어 불리하다. 반면 다음과 같이 정의하면 현재 구현된 기술과 시장 요구가 더 잘 맞는다.

> 민감한 업무 데이터를 외부 클라우드에 맡기지 않고, 조직·방·좌석·회의·교육·업무 상태를 하나의 공간으로 운영하는 프라이빗 협업 플랫폼

제품의 핵심 경쟁력은 3D 자체가 아니라 다음 세 가지의 결합이다.

1. 외부 SaaS에 의존하지 않는 온프레미스 협업
2. 조직과 실제 공간을 반영한 고객 전용 업무환경
3. 고객 서버에서 직접 통제하는 화상·음성·화면공유와 업무 데이터

따라서 초기 시장은 모든 일반기업이 아니라, 외부 SaaS 사용이 어렵거나 여러 장소의 협업을 공간 단위로 운영해야 하는 조직에 집중하는 것이 적합하다.

### 2.1 우선 공략을 권장하는 시장

#### 중소·중견 제조업 연구개발 조직

- 공장, 본사, 연구소가 서로 떨어진 경우가 많다.
- 도면·제품 화면공유와 긴급 기술협업이 빈번하다.
- 가상 출근보다 **원격 기술협업 워룸**으로 제안하는 것이 효과적이다.

#### 직업학교·기업 연수원

- 교실, 실습실, 강당이라는 공간 구조가 현재 건물·방 체계와 자연스럽게 맞는다.
- 일반 LMS와 달리 함께 접속하고 있다는 현장감을 제공할 수 있다.
- 출결, 팀별 공간, 화면공유, 타운홀을 하나의 교육 패키지로 구성할 수 있다.

#### 방산 협력사·보안 연구소·폐쇄망 조직

- 온프레미스 DB와 자체 LiveKit SFU가 가장 강한 차별점이 된다.
- 사내망 전용, VPN 접근, 내부망·DMZ 분리 형태로 공급할 수 있다.
- 다만 폐쇄망 자체가 보안을 보장하지 않으므로 사용자·장치 검증, 최소 권한, 감사 체계를 함께 제시해야 한다.

미 국방부의 Zero Trust 전략도 네트워크 안에 있다는 이유만으로 사용자를 신뢰하지 않고, 온프레미스와 외부 환경을 모두 세분화·격리하며 정책에 따라 통제하는 방향을 제시한다.  
참고: [미 국방부 Zero Trust 전략](https://dodcio.defense.gov/Portals/0/Documents/Library/DoD-ZTStrategy.pdf)

### 2.2 병원·의료 분야 진입 시 주의점

병원은 잠재력이 크지만 초기부터 원격진료 제품으로 판매하는 것은 권장하지 않는다. 먼저 다음 범위로 진입하는 것이 현실적이다.

- 의료진 교육
- 병원 내부 회의
- 연구 협업
- 다기관 비임상 프로젝트

환자 개인정보, 의료영상 또는 진료정보가 들어가면 접근통제, 암호화, 감사, 보존·삭제 정책과 법률 검토가 필요하다. 기술만 설치하는 것으로 충분하지 않다.  
참고: [HHS 원격의료 개인정보·보안 가이드](https://telehealth.hhs.gov/providers/best-practice-guides/privacy-and-security-telehealth)

## 3. 현재 제품의 강점

### 3.1 온프레미스 구축

- 업무 DB, 채팅, 근태, 조직정보를 고객 서버에 저장한다.
- LiveKit까지 자체 구동해 영상과 음성을 외부 SaaS 계정에 맡기지 않을 수 있다.
- 인터넷이 제한된 사내망 또는 VPN 환경에도 적용할 수 있다.
- 서버, 계약, 건물 구성과 라이선스를 함께 통제할 수 있다.

일반 소비자에게는 큰 차이가 아닐 수 있지만, 보안팀과 IT 관리자가 구매 결정에 참여하는 조직에는 명확한 장점이다. 하이브리드 업무가 사내 네트워크와 온프레미스 인프라 투자를 계속 요구한다는 업계 조사도 있다.  
참고: [Cisco 하이브리드 업무 인프라 보고서](https://www.cisco.com/c/en_uk/solutions/enterprise-networks/hybrid-work-network-ema-report.html)

### 3.2 공간과 실제 업무 기능의 결합

현재 제품은 단순한 3D 배경이 아니다. 다음 기능이 실제 방 ID를 중심으로 연결된다.

- 층과 방
- 조직과 좌석
- 방별 화상회의, 화면공유와 채팅
- 회의 예약과 팀별 임박 알림
- 화이트보드와 디지털 게시판
- 출퇴근과 실시간 근무 상태
- 타운홀과 외부 게스트 행사
- 방별 시설과 접근 정책

이 구조는 기존 화상회의 도구가 제공하기 어려운 **공간 기반 업무 맥락**을 만들 수 있다.

### 3.3 고객별 맞춤 건물

- 건물 프리셋을 계약과 라이선스에 연결할 수 있다.
- 고객별 전용 공간을 독립적으로 구성해 납품할 수 있다.
- 일반 SaaS 구독 외에도 구축비, 맞춤 설계비, 유지보수 계약을 만들 수 있다.

### 3.4 자체 설치·백업·복구 기반

- Windows 단일 설치 프로그램과 포터블 ZIP을 제공한다.
- 초기 DB, 백업·복원, 하드웨어 라이선스와 터널 설정 체계가 있다.
- Node.js, SQLite와 LiveKit 실행 파일을 포함해 외부 프로그램 설치 의존성을 낮췄다.

이는 개발 시제품과 실제 납품 제품을 구분하는 중요한 기반이다.

## 4. 현재 제품의 약점과 위험

### 4.1 기능이 많아 핵심 가치가 흐려질 수 있음

가상오피스, 근태, 회의, 타운홀, 건물 스튜디오, 라이선스, 게시판과 교육 기능을 한꺼번에 설명하면 고객이 제품의 핵심을 이해하기 어렵다.

영업 메시지는 다음처럼 단순화할 필요가 있다.

> 민감한 업무 데이터를 외부 클라우드에 맡기지 않고 운영하는 공간형 사내 협업 서버

`메타버스`를 전면에 내세우면 일부 기업은 게임이나 일회성 이벤트 도구로 오해할 수 있다. 3D는 제품의 목적이 아니라 협업 상황을 이해시키는 사용자 경험으로 설명하는 편이 좋다.

### 4.2 기존 화상회의보다 복잡한 사용 흐름

사용자는 단순히 회의에 참여하려는데 층 이동, 방 선택, 캐릭터 이동, 스크린 클릭이 추가될 수 있다. 공간성이 가치를 주는 업무에는 장점이지만 단순 회의에는 불편하다.

다음 두 가지 흐름을 항상 함께 제공해야 한다.

1. 3D 공간에서 실제 방으로 이동해 참여
2. 대시보드 일정·알림에서 즉시 참여

3D 공간을 반드시 거치게 하면 장기적으로 사용 이탈 요인이 될 수 있다.

### 4.3 브라우저와 모바일 자원 소모

3D 렌더링과 WebRTC를 동시에 실행하면 GPU, CPU와 배터리를 사용한다. 특히 모바일 발열과 배터리 소모는 제품 만족도에 직접 영향을 준다.

개선이 필요한 항목:

- 회의창을 열었을 때 3D 렌더러 완전 일시정지
- 백그라운드 탭 FPS를 0~1로 제한
- 모바일·저사양 자동 모드
- 원거리 아바타 LOD
- 그림자, 후처리, 텍스처 해상도 자동 축소
- 3D 없이 업무 기능만 사용하는 2D 경량 모드

### 4.4 온프레미스에 대한 과신 위험

온프레미스는 데이터 통제에는 유리하지만 고객 서버가 침해되면 전체 시스템이 노출될 수 있다. 계정 탈취, 관리자 권한 오용, 패치 지연, 백업 유출과 터널 토큰 탈취 위험도 있다.

고보안 시장에서 요구될 항목:

- AD/LDAP 또는 SAML/OIDC SSO
- 다중 인증(MFA)
- 역할 기반 접근통제와 최소 권한
- 관리자 행위와 로그인 감사 로그
- 화면공유, 파일과 회의 이력
- 보안 이벤트·Syslog 내보내기
- 비밀키 암호화 저장과 주기적 교체
- 취약점 점검과 SBOM
- 보안 패치·지원 종료 정책
- 망 분리·DMZ 배치 기준
- 정기적인 백업 복구와 장애 대응 훈련

참고: [미 국방부 Zero Trust 설명](https://www.defense.gov/News/News-Stories/Article/Article/4078717/zero-trust-architecture-could-prevent-adversary-data-theft-protect-warfighters/)

### 4.5 기존 기업 시스템과의 연동 부족

기업은 새로운 시스템에 조직정보를 다시 입력하고 싶어 하지 않는다. 실제 영업 과정에서 다음 연동 요구가 발생할 가능성이 크다.

- Microsoft Entra ID·Active Directory
- Google Workspace
- 사내 그룹웨어
- HR 인사 DB
- Outlook·Google Calendar
- 전자결재
- SIEM·Syslog
- NAS·문서관리시스템

연동이 부족하면 기능이 좋아도 고객은 관리할 시스템이 하나 더 늘어난다고 판단할 수 있다.

### 4.6 고가용성과 대규모 운영 증거 부족

현재 구조는 단일 고객 서버 중심 구축에는 적합하지만 대기업은 다음 항목을 요구한다.

- 서버 장애 시 자동 전환
- DB 시점 복구
- LiveKit 장애 복구
- 동시 접속자별 부하 시험 결과
- 패킷 손실·TURN 사용 시 품질 자료
- 서버·미디어 모니터링 대시보드
- 장애 대응 SLA

`최대 100명`이라는 설명보다 시험 장비, 네트워크, 영상 품질과 동시 송출 수를 명시한 측정 결과가 더 중요하다.

## 7. 최종 평가

현재 WorkNexus는 **모든 회사를 위한 범용 가상오피스**로 판매할 경우 기존 화상회의와 협업 제품에 비해 복잡하고, 3D 성능과 연동 부족이 약점이 된다.

반면 다음 조건을 가진 조직에는 분명한 경쟁력이 있다.

- 외부 SaaS 사용이 어렵다.
- 여러 장소의 직원이 공간과 팀 단위로 협업한다.
- 고객 전용 건물과 업무 흐름이 필요하다.
- 데이터와 미디어 서버를 회사가 직접 통제해야 한다.
- 일반 화상회의보다 상시적인 조직 존재감과 현장성이 중요하다.

따라서 향후 개발과 영업은 `메타버스 기능의 수`를 늘리는 방향보다 다음에 집중해야 한다.

1. 미디어와 실시간 상태의 안정성
2. 모바일·저사양 성능
3. 기업 인증·감사·보안 체계
4. 기존 조직·일정 시스템 연동
5. 업종별 목적이 선명한 패키지와 데모
6. 설치·백업·장애 복구의 제품화

WorkNexus의 가장 설득력 있는 정체성은 다음과 같다.

> **프라이빗 협업 인프라에 공간 경험을 결합한 온프레미스 업무 플랫폼**

이 방향으로 제품 메시지와 개발 우선순위를 정렬하면 일반적인 가상오피스보다 경쟁 대상을 줄이고, 보안·맞춤 구축·현장 협업이라는 지불 의사가 있는 시장에 집중할 수 있다.

## 8. 30명 실시간 미디어 반복 부하 검증 결과 (2026-09-30)

가장 먼저 추진할 개선 항목으로 제안한 `회의·화면공유·음성·카메라 자동 회귀 테스트`를 실제 LiveKit SFU와 실제 Chrome WebRTC 연결로 구현했다. API 응답만 확인하는 모의 시험이 아니라, 30개 참여자가 트랙을 발행하고 상대 트랙을 구독하는지를 브라우저에서 직접 확인한다.

### 8.1 시험 시나리오

30명의 사용자가 다음 흐름을 10회 연속 반복했다.

1. 3D 오피스의 같은 방에서 근처 대화 연결
2. 각 사용자가 마이크 트랙을 발행하고 나머지 29명의 마이크 수신 확인
3. 근처 대화 종료 후 회의실 LiveKit 방 입장
4. 30명 마이크 발행, 6명 카메라 발행
5. 발표자 화면 영상과 시스템 오디오 송출
6. 모든 참여자의 화면 영상·공유 오디오·상대 마이크·카메라 수신 확인
7. 공유 종료, 회의 퇴장 및 다음 회차 재입장

### 8.2 결과

| 항목 | 결과 |
|---|---:|
| 참여자 | 30명 |
| 반복 횟수 | 10회 |
| 근처 대화 연결 | 300회 성공 |
| 회의실 연결 | 300회 성공 |
| 화면 영상·시스템 오디오 수신 | 300명분 성공 |
| 초기 연결 재시도 | 0회 |
| 실행 중 자동복구 | 0회 |
| 최종 판정 | 10/10회 통과 |

| 전체 준비 완료 시간 | 평균 | 최소 | 최대 |
|---|---:|---:|---:|
| 근처 대화 | 5.0초 | 3.2초 | 9.3초 |
| 회의·화면·공유 오디오 | 5.0초 | 3.5초 | 6.7초 |

첫 장시간 예비 실행에서는 3회차에 참여자 한 명이 중간 이탈한 사례가 한 번 있었다. 시험 도구에 런타임 이탈 감지와 개별 재연결 검증을 추가한 후 처음부터 다시 실행했으며, 최종 10회 시험에서는 이탈이나 자동복구 개입 없이 모두 통과했다. 순간 부하에 따라 근처 대화 전체 구독 완료 시간이 최대 9.3초까지 증가한 점은 운영 UI의 연결 준비 표시와 장시간 시험에서 계속 관찰해야 한다.

### 8.3 해석과 다음 검증

이 결과로 단일 개발 노트북과 로컬 설치형 LiveKit 환경에서 30명 규모의 핵심 미디어 흐름이 반복 동작함을 확인했다. 다만 한 Chrome 프로세스에서 참여자를 생성한 시험이므로 30대의 실제 PC·모바일, 서로 다른 통신사, 회사 방화벽, TURN 경로를 완전히 대체하지는 않는다.

다음 우선순위는 다음과 같다.

1. 1~2시간 또는 100회 이상의 장시간 안정성 시험
2. 타운홀 100명·200명·300명 단계별 수신 부하와 노트북 자원 한계 측정
3. 외부망·LTE/5G·iPhone·TURN/TLS 실제 단말 교차 시험
4. 재연결 중 UI 표시와 제한시간 초과 시 토큰 재발급·재입장 검증
5. 다수 카메라의 선택 구독, 화질 단계 조절과 모바일 발열 최적화

재현 명령은 `npm run test:media-stress-30`이며 상세 결과는 실행 후 `test-results/media-stress-30.json`에 생성된다.

### 8.4 타운홀 100명·200명·300명 단계 시험 (2026-09-30)

소수 발표자가 하나의 화면 영상과 시스템 오디오를 송출하고 다수 청중이 구독하는 타운홀 구조를 같은 개발 노트북에서 시험했다.

| 규모 | 검증 경로 | 결과 | 준비 완료 | 작업 메모리 참고값 |
|---:|---|---|---:|---:|
| 100명 | 예약·게스트 등록·티켓·토큰을 포함한 전체 제품 경로 | 100/100 접속, 99/99 A/V 수신 성공 | 23.1초 | 약 1.75GB |
| 200명 | LiveKit SFU 용량 경로 | 200/200 접속, 199/199 A/V 수신 성공 | 44.8초 | 약 2.64GB |
| 250명 | LiveKit SFU 용량 경로 | 250/250 접속, 249/249 A/V 수신 성공 | 56.1초 | 약 3.25GB, 평균 3.94 CPU 코어 |
| 300명 | Chrome 2개에 150명씩 분산한 동일 SFU 방 | 300/300 접속, 299/299 A/V 수신 성공 | 각 부하 발생기 53.1초·60.6초 | 프로세스별 측정 |

한 Chrome 프로세스에서는 260명과 300명을 요청해도 모두 253개 연결에서 멈췄다. 이는 LiveKit 서버의 참가자 한도가 아니라 DevTools·Vite 연결을 포함해 약 255개에서 나타나는 Chrome 단일 프로세스 WebSocket 경계로 판단된다. 독립 Chrome 두 개로 분리하자 같은 노트북과 같은 LiveKit 방에서 300명이 통과했다.

현재 제품의 타운홀 예약·세션 코드는 100명을 상한으로 강제하므로 **현재 판매·운영 가능한 제품 한도는 100명**이다. *(2026-10-12 현행화: 이후 제품 정책을 바꿔 현재 타운홀 한도는 200명이며, 200명 실제 앱 흐름 시험을 통과했다 — 0장·10번 문서 5.1.)* 200명과 300명 결과는 SFU와 노트북의 기술적 여유를 확인한 것이며, 제품 지원 인원을 확대하려면 라이선스·계약 포털·DB·좌석 UI·API 상한을 함께 변경하고 1080p 및 실제 외부망으로 다시 검증해야 한다.

이번 시험은 320×180, 4fps 합성 화면과 합성 오디오 한 개를 로컬 루프백에서 수신한 결과다. 실제 1080p 영상, 서로 다른 통신사와 TURN, 모바일 300대의 발열·디코딩 성능 및 인터넷 업·다운로드 대역폭을 보증하지 않는다.

| 가격 | 가격 초안(구독형·구매형) | 초안은 동시접속 **20/50/100명**인데 라이선스 포털은 **100/200/300명**만 고를 수 있었다. 제품명도 옛 이름(워크버스). → **2026-10-12 결정: 50/100/200/300**(17번 문서), 포털·계약 API에 50 반영 |
| 운영 | 공급자 포털(계약·라이선스·릴리스), 고객 다운로드 포털, WSL2 Linux 빌드 | 파일럿 사용 지표를 모을 방법(현재 원격 수집 기능 없음), 원격 지원 절차, 장애 대응 연락 체계 |

> **결론**: 기능보다 먼저 ① 상시 라이브 체험 서버, ② 가격·라이선스 단계 정렬, ③ 파일럿 계약·측정 도구 세 가지를 갖춰야 사용자 모집을 시작할 수 있다.

### 9.2 전체 흐름 — 5단계

```text
0단계 우리가 먼저 쓴다(도그푸딩, 2주)
  → 1단계 디자인 파트너 3~5곳 무료 파일럿(4주)
  → 2단계 정기 라이브 시연으로 관심 고객 모으기(상시)
  → 3단계 사례·수치를 무기로 광고·콘텐츠 확대
  → 4단계 직접 영업 + 지역 IT 파트너 판매, 이후 공공 조달 준비
```

각 단계는 "다음 단계로 넘어가는 조건"을 두고, 조건을 채우지 못하면 광고비를 쓰기 전에 제품을 먼저 고친다.

### 9.3 0단계 — 우리가 먼저 쓴다 (도그푸딩, 2주)

- **목적**: 고객보다 먼저 불편과 장애를 찾는다. 판매자가 매일 쓰지 않는 제품은 설득력이 약하다.
- **방법**
  - 상시 서버 1대(9.7절 장비)에 정식 운영판(production)을 설치하고 칼라무스·관계사(예: 유진IT) 인원이 매일 출근·회의·화면공유를 WorkNexus로 한다.
  - 외부 미팅·고객 시연도 이 서버의 회의실·타운홀에서 진행한다(시연 자체가 실사용 증거가 된다).
  - 매일 불편 사항을 한 줄씩 기록하고 주 1회 묶어서 수정한다.
- **다음 단계 조건**: 2주 동안 치명 장애(서버 재시작 필요, 회의 연결 실패 반복) 0건, 주요 불편 사항 수정 완료.

### 9.4 1단계 — 디자인 파트너 파일럿 (3~5곳, 4주)

**누구를 모을까** — 10번 문서의 1차 고객군(제조·연구)과 2차(연수원·교육)를 중심으로, 의사결정이 빠른 곳부터.

| 모집 경로 | 대상 | 접근 방법 |
|---|---|---|
| 지인·관계사 네트워크 | 대표가 직접 아는 중소·중견기업, 거래처 | 대표가 직접 1:1 제안. 가장 빠르고 신뢰가 높다 |
| IT 유지보수·SI 업체 | 지역 전산 유지보수 업체가 관리하는 고객사 | 업체에 "고객사 파일럿 + 판매 수수료" 제안. 설치를 대신 맡아 줄 파트너 후보이기도 하다 |
| 산업단지·제조업 협회 | 본사·공장이 분리된 제조사 | 협회 소식지·세미나에서 15분 발표 기회 확보 |
| 직업훈련기관·기업 연수원 | 교실·실습실·강당 구조를 가진 교육 조직 | 교육 담당자에게 "온라인 연수 캠퍼스" 제안. 타운홀(200명)이 강점 |
| 창업보육센터·공유오피스 | 입주기업이 많은 기관 | 기관 단위로 "가상 입주 사옥" 제공, 입주기업 여러 곳을 한 번에 확보 |

**조건(파트너가 주는 것 / 우리가 주는 것)**

| 파트너가 약속 | 우리가 제공 |
|---|---|
| 실사용 10명 이상, 4주 동안 주 3일 이상 사용 | 4주 무료(또는 30만 원, 본계약 시 전액 차감 — 가격 초안 기준) |
| 주 1회 30분 피드백 통화 | 원격 설치·교육, 전용 지원 채널(카카오톡 채널 또는 이메일) |
| 종료 후 사례 공개(익명 가능)·인터뷰 동의 | **파운딩 고객 가격**: 본계약 첫해 30~50% 할인 또는 가격 고정 |
| 보안팀 사전검토 질문 회신 | 업종 맞춤 건물 1개 무상 구성 |

**4주 진행표**

| 주차 | 할 일 | 산출물 |
|---|---|---|
| 0주 | IT 사전질문서·보안 검토(08 가이드), 서버 준비, 원격 설치, 건물 구성 | 설치 완료 검수표(11번 매뉴얼) |
| 1주 | 관리자·사용자 30분 교육, 첫 회의 함께 진행 | 교육 참석자, 첫 회의까지 걸린 시간 |
| 2~3주 | 일상 사용, 주 1회 피드백 통화, 문제 즉시 수정·업데이트 | 주간 지표표, 문제 목록 |
| 4주 | 종료 인터뷰, 계속 쓸지·얼마면 살지 질문 | 파일럿 결과 보고서, 사례 초안 |

**측정할 지표** (파일럿 성공 판단)

| 지표 | 목표(예) | 측정 방법 |
|---|---|---|
| 주간 활성 사용자 / 등록 사용자 | 60% 이상 | 근태 CSV(출근 기록) |
| 핵심 회의 성공률 | 95% 이상 | 회의 기록 + 파트너 보고 |
| 첫 회의까지 걸린 시간 | 설치 후 1일 이내 | 진행표 |
| 지원 문의·장애 | 주 2건 이하, 치명 장애 0 | 지원 채널 기록 |
| 계속 사용 의향 | "없어지면 아쉽다" 40% 이상 | 종료 설문 |
| 유료 전환 의사 | 5곳 중 2곳 이상 | 종료 인터뷰 |

> 현재는 고객 서버의 사용 통계를 원격으로 모으는 기능이 없다(고객 데이터가 밖으로 나가지 않는 것이 제품 원칙). 그래서 **관리자가 직접 내보내는 "파일럿 사용 리포트"**(로그인·회의·화면공유 횟수, 연결 실패, 재접속 수만 집계, 개인 대화 내용 없음)를 만드는 것을 10.1절에서 제안한다.

**다음 단계 조건**: 파트너 3곳 이상 4주 완주, 2곳 이상 유료 전환 의사, 공개 가능한 사례 1건.

### 9.5 2단계 — 정기 라이브 시연으로 관심 고객 모으기

공개 체험 사이트만으로는 "혼자 둘러보는" 경험이라 실시간 협업의 가치가 전달되지 않는다. **정해진 시간에 여러 사람이 함께 들어오는 시연**이 가장 효과적이다.

- **매주 1회 30분 "라이브 오피스 투어"**(예: 목요일 오후 4시): 상시 라이브 서버의 타운홀에서 진행. 참가자는 게스트 링크로 바로 입장해 반응(👏·❓) 보내기, 질문하기, 소회의실 이동·화면공유를 직접 해 본다.
- **시연 자체가 제품 증명**: 웨비나 도구를 따로 쓰지 않고 WorkNexus 타운홀로 진행한다.
- **신청 경로**: 소개 페이지 "라이브 시연 신청" → 이메일 수집 → 시연 후 15분 1:1 상담 예약 → 파일럿 제안.
- **업종별 회차**: 제조 워룸 / 연수 캠퍼스 / 보안·폐쇄망 순으로 돌려 업종에 맞는 건물로 시연한다.

### 9.6 3단계 — 광고·홍보 (사례가 생긴 뒤 확대)

광고는 **파일럿 사례 1건 이상이 생긴 뒤** 본격적으로 한다. 그 전에는 소액 시험만 한다.

**콘텐츠** (우리가 이미 가진 강점: 촬영 스튜디오로 실제 앱 영상을 저비용으로 만들 수 있다)

| 콘텐츠 | 내용 | 쓰는 곳 |
|---|---|---|
| 업종별 60초 영상 3편 | 제조 워룸·연수 캠퍼스·폐쇄망 협업 | 유튜브 쇼츠, 소개 페이지, 영업 메일 |
| 기술·검증 글 월 2편 | 부하 시험(30명·100명·200명), 폐쇄망 구성, 보안 Q&A(08 가이드 요약) | 네이버 블로그·브런치·링크드인 |
| 보안팀 사전검토 패키지 | 08 보안 가이드 + 데이터 흐름도 + 포트표 + 설치 검수표를 한 PDF로 | **다운로드 시 이메일 입력**(관심 고객 확보 수단) |
| 고객 사례 | 파일럿 결과(익명 가능): 문제 → 도입 → 수치 | 소개 페이지, 영업 자료 |
| 월 1회 웨비나 | 9.5절 라이브 시연의 확장판, 파트너 고객 초청 | 신청 페이지 |

**유료 광고 — 소액 시험부터**

| 채널 | 왜 | 시작 예산(월) | 판단 기준 |
|---|---|---|---|
| 네이버 검색광고 | 국내 B2B 구매 담당자가 검색으로 찾는다. 키워드: 온프레미스 화상회의, 폐쇄망 화상회의, 사내 가상오피스, 구축형 메타버스, 사내망 화상회의 | 30~50만 원 | 시연 신청 1건당 비용 |
| 유튜브(쇼츠·인스트림) | 이미 만든 영상 활용, 업종 타깃팅 | 20~30만 원 | 시청 완료율, 소개 페이지 유입 |
| 링크드인(대표 계정, 유기적) | 개발·검증 일지로 신뢰 축적 | 0원 | 문의 수 |

- 3개월 시험 후 **시연 신청 1건당 비용**이 가장 낮은 채널에 집중한다.
- "메타버스"만 단독으로 쓰는 광고 문구는 피한다(게임·이벤트로 오해). "구축형", "온프레미스", "폐쇄망", "사내망"을 함께 쓴다.
- 과장 표현 금지 원칙(10번 문서 5.3)을 광고 문구에도 똑같이 적용한다.

**전시회·행사** — 사례 1~2건이 생긴 뒤 업종 전시회(스마트공장·제조, 보안, 에듀테크 분야)에 참가한다. 부스에서는 노트북 한 대로 라이브 서버에 접속해 "지금 이 공간에 본사·공장 직원이 있다"를 보여 준다.

### 9.7 4단계 — 판매

**판매 경로**

1. **직접 영업**(초기): 대표가 시연 → 파일럿 → 계약까지 직접 진행. 첫 5~10개 고객은 이 방식이 가장 빠르다.
2. **지역 IT 파트너(리셀러)**(확장): 온프레미스 제품은 고객 근처에서 설치·장애 대응을 해 줄 사람이 필요하다. 지역 IT 유지보수·SI 업체를 파트너로 두고 판매 수수료(예: 20~30%)와 설치·유지보수 매출을 나눈다. 파트너용 설치 교육·인증(반나절)과 파트너 포털 계정을 제공한다.
3. **공공·조달**(중장기): 공공기관·학교는 조달 절차가 필요하다. 소프트웨어 품질인증(GS인증) 등 공공 판매에 필요한 인증·등록 요건과 비용·기간을 먼저 조사하고, 사례가 쌓인 뒤 착수한다. *(요건은 바뀔 수 있으므로 착수 전에 확인한다.)*

**가격 정렬** — 판매 전에 반드시 정리할 것

- 가격 초안(동시접속 20/50/100)과 라이선스 포털(100/200/300)을 맞춘다. → **2026-10-12 결정: 50/100/200/300 네 단계**(20명은 너무 적어 제외). 가격은 `17. WorkNexus 가격 정책 개정안_20261012.md`, 포털 계약 화면·계약 API에 50을 반영했다(고객 서버는 1~300을 이미 지원).
- 가격 초안의 제품명(워크버스)을 WorkNexus로 바꾸고, "클라우드 사용료 없음"은 "WorkNexus 사용료 외 별도 클라우드 구독료 없음(서버·회선·전기는 고객 부담)"으로 정확히 쓴다.
- 파일럿 가격(무료 또는 30만 원, 본계약 시 차감)과 파운딩 고객 할인을 확정한다.

**영업 도구**

| 도구 | 상태 | 할 일 |
|---|---|---|
| 15분 시연 대본(업종별 3종) | 10번 문서에 기본안 | 라이브 서버 건물에 맞춰 확정 |
| TCO 계산표 | 없음 | 고객 인원·기존 화상회의 구독료 입력 → 3년 비용 비교(엑셀 또는 소개 페이지 계산기) |
| 보안팀 사전검토 패키지 | 08 가이드 등 흩어져 있음 | 한 PDF로 묶기 |
| 파일럿 계약서·본계약서·이용약관·개인정보 처리 안내 | 없음 | 전문가 검토 후 템플릿화 |
| 설치 완료 검수표 | 있음(11번 매뉴얼) | 파일럿에 그대로 사용 |

### 9.8 필요한 장비·예산 (대략)

| 항목 | 내용 | 대략 비용 |

## 10. 판매를 돕는 추가 개발 제안 (2026-10-12 추가)

판매·파일럿 진행에 직접 영향을 주는 순서로 정리했다. 모두 착수 전에 범위를 다시 확인한다.

### 10.1 우선 (파일럿 시작 전)

1. **라이브 체험 사옥 모드**: 상시 서버에서 데모 계정 자동 배정, 정해진 시간마다 데이터 초기화, 동시 접속 제한, 게스트 링크 바로 입장. 9.5절 정기 시연의 기반.
2. **파일럿 사용 리포트 내보내기**: 관리자 콘솔에서 기간을 정해 로그인·회의·화면공유 횟수, 연결 실패·재접속 수, 활성 사용자 수를 CSV/PDF로 내보낸다. 개인 대화·화면 내용은 넣지 않는다. 고객이 직접 내보내 우리에게 주는 방식이라 "데이터가 밖으로 나가지 않는다"는 원칙을 지킨다.
3. ✅ **라이선스 단계 50 추가**(공급자 포털 계약 화면·계약 API `functions/api/manage/contracts`, 2026-10-12): 가격표(50/100/200/300)와 맞춤. 고객 서버는 이미 지원한다.
4. **2D 바로 참여 흐름 강화**: 대시보드 일정·알림에서 3D를 거치지 않고 회의에 바로 들어가는 경로를 모든 회의에 일관되게 제공(4.2절의 이탈 위험 대응).

### 10.2 다음 (첫 유료 고객 전후)

5. ✅ **캘린더 연동 1단계**(2026-10-12): 팀·전사 일정 달력과 벽 일정 보드, 일정마다 구글 캘린더에 추가·`.ics` 내보내기(한 방향). 양방향 동기화는 하지 않기로 함(18번 문서 5장).
6. **OIDC SSO + 관리자 MFA**(Secure 패키지 전제): 보안팀 질문에서 가장 먼저 나오는 항목.
7. **업종별 시작 프리셋 3종**: 제조 워룸·연수 캠퍼스·보안 협업 건물과 메뉴 용어 묶음. 설치 직후 "자기 업무용"으로 보이게 한다.
8. **원격 업데이트 안내**: 관리자 콘솔에 새 버전·보안 업데이트 알림(공급자 포털 릴리스 정보 조회). 업데이트 실행은 지금처럼 고객이 직접.

### 10.3 중장기

9. LDAP/AD 연동, Syslog 내보내기, SBOM 공개
