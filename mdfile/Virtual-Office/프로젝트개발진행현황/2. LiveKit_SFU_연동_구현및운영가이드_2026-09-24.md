# LiveKit SFU 연동 · 구현 및 운영 가이드

최종 현행화: 2026-09-26 (모든 음성·카메라·화면공유 LiveKit 단일화, 1:1 통화·방 안 근처 대화·방 카메라 추가, P2P 경로 완전 제거)
대상: 고객 설치 서버 관리자, 미디어 인프라 담당자, 사내 IT 운영자 (추후 마케팅 기술설명 자료로 재사용 가능하도록 정리)

## 0. 한 줄 요약

Calamus Virtual Office의 **모든 음성·카메라·화면공유(영상 + 공유 소리)는 LiveKit SFU 하나로 전송**한다. 회의실 화면공유, 회의 창 마이크·카메라, 1:1 화면공유, 1:1 음성·영상 통화, 방 안 근처 대화, 머리 위 카메라, 타운홀까지 예외가 없다. 사용자 단말끼리 직접 연결하는 P2P 경로와 P2P 신호 중계는 2026-09-26에 완전히 제거했다. LiveKit은 고객사 사내 서버 안에서 자체 구동되며(Docker·외부 클라우드 계정·월 사용료 불필요), 각 사용자는 자기 음성·영상을 한 번만 서버로 올리고 서버가 필요한 사람에게만 나눠 준다.

## 2. Windows 설치 패키지(Setup.exe) 무설치 자동 연동 (⭐ 기본 권장)

### 2.1 Docker/외부 도구 불필요 (Zero-Dependency)
- 과거 LiveKit 구동을 위해 필요했던 **Docker Desktop, Linux 가상머신(WSL2), Redis 설치가 일체 필요 없습니다.**
- Go 언어로 단일 정적 빌드된 **Windows 네이티브 `livekit-server.exe` (v1.13.7, 56.4MB)** 바이너리가 설치 패키지에 포함됩니다. API 키가 들어 있는 YAML은 패키지에 포함하지 않습니다.
- 고객사 서버 PC에서 **`Setup.exe`** 를 실행하여 설치를 완료하거나 **`VirtualOfficeServer.exe`** 를 더블클릭하면:
  1. Node.js 백엔드 웹 서버 (포트 3001) 자동 실행
  2. **LiveKit SFU 미디어 서버 (포트 7880)** 백그라운드 동시 자동 실행
  3. 사내망 접속 사원들에게 7880 포트 SFU 주소 자동 중계

### 2.2 설치별 자격 증명 자동 생성
- 첫 실행 시 암호학적 난수로 설치 전용 API key와 48바이트 secret을 생성합니다. 모든 고객이 공유하는 기본 키는 없습니다.
- 자격 증명은 `server/data/livekit/credentials.json`, LiveKit 실행 설정은 `server/data/livekit/livekit.runtime.yaml`에 생성됩니다.
- 두 파일은 패키지 생성물과 Git 저장소에 포함하지 않으며, 로그·관리자 UI에도 secret을 출력하지 않습니다.
- 같은 설치에서는 재시작 후 기존 키를 재사용하고, 서로 다른 설치에서는 서로 다른 키를 생성합니다.
- `LIVEKIT_API_KEY`와 `LIVEKIT_API_SECRET`으로 외부 키를 지정하려면 반드시 둘을 함께 설정해야 합니다. 하나만 있거나 안전 기준에 미달하면 서버는 시작 단계에서 실패 처리합니다.
- 기본 포트: `7880` (WebSocket / HTTP API), `7881` (TCP RTC Fallback)
- 서버가 클라이언트의 접속 헤더(사내망 IP 등)를 기반으로 `ws://[서버IP]:7880` 미디어 URL을 자동 계산하므로, 복잡한 `.env` 설정 없이 설치 즉시 30~100인 화면 공유가 동작합니다.

## 3. 권한·한도 모델

토큰에는 "발행할 수 있는 트랙 종류"가 들어간다. 서버가 역할에 따라 정하며 클라이언트가 바꿀 수 없다.

| 역할 | 쓰는 곳 | 발행 가능 |
| --- | --- | --- |
| `host`, `cohost`, `presenter` (타운홀) | 타운홀 | 카메라·마이크·화면·화면 소리 |
| `presenter` (회의실) | 회의실 화면공유 시작자 | 카메라·마이크·화면·화면 소리 |
| `meeting` | 회의 창에 참여한 사람 | 카메라·마이크 |
| `attendee` | 3D 벽 스크린·미리보기만 보는 사람 | 없음(시청 전용) |
| `direct` | 1:1 화면공유·통화의 두 사람 | 카메라·마이크·화면·화면 소리 |
| `nearby` | 방 안 근처 대화·머리 위 카메라 | 카메라(항상) + 마이크(관리자가 허용한 방만) |

- 토큰 기본 TTL: `LIVEKIT_TOKEN_TTL_SECONDS=600`(10분), 서버가 60~3600초 범위로 안전하게 제어합니다.
- 타운홀은 최대 100명 수용, 발표자 최대 4명 한도를 적용합니다.
- 공용 화면 공유 슬롯은 계약의 `maxConcurrentSharedScreens`를 확인합니다.
- 관리자가 발표 권한을 취소하거나 음소거 시 SQLite 상태 갱신과 동시에 LiveKit `UpdateParticipant` API를 원격 호출하여 미디어 트랙을 즉시 차단합니다.

## 4. 왜 모든 음성·영상을 LiveKit SFU로 통일했는가

### 4.1 P2P WebRTC의 근본적인 한계 — 발표자 PC가 시청자 수만큼 일을 한다
- **P2P Mesh WebRTC의 구조**: P2P 방식은 발표자 브라우저가 화면 비디오 스트림을 시청자 수(N-1)만큼 **직접 인코딩해서 업로드**한다. FHD(1080p) 화면 공유 시 스트림당 약 3~4Mbps의 대역폭이 소모된다.
- 시청자가 4~6명만 넘어도 송출자 업로드 대역폭이 20~30Mbps를 초과하며 브라우저 렌더링 탭이 멈추거나 심각한 패킷 드롭이 발생한다 — 실제로 고사양 게이밍 PC가 발표자일 때는 문제없다가, 저사양 노트북이 발표자가 되는 순간 시청자 4명부터 심하게 버벅이는 현상으로 확인됐다.
- 반면 **LiveKit SFU**는 발표자가 단 1개의 스트림만 SFU 서버로 업로드하면, 서버가 각 시청자에게 패킷을 복제·분배하므로 발표자 PC 부하 없이 30~100인 이상 안정적인 화면 공유가 가능하다.

### 4.2 회의실·화면공유는 "선택"이 아니라 "항상 SFU"로 고정했다
과거에는 방마다 "⚡ LiveKit SFU (대규모)" / "🔗 P2P 직결 (최대 6인)"을 관리자가 직접 고르게 하는 토글이 있었다. 하지만 실제 운영에서는 문제가 있었다:

1. **회의실은 몇 명이 들어올지 미리 알 수 없다.** 소회의실로 만든 방도 어느 날 6명을 넘길 수 있고, 그 순간 P2P를 선택해둔 발표자의 PC가 버벅이기 시작한다.
2. **선택 UI가 있다는 것 자체가 운영 리스크다.** 관리자가 실수로 P2P를 선택하면 장애로 이어지는데, 이걸 막으려고 "6인 초과 시 자동으로 SFU로 승격"하는 가드레일까지 만들어야 했다 — 구조가 복잡해지고, 승격 판정 로직에도 버그가 있었다(순간 스냅샷 기준으로 판정해 실시간 시청자 수와 어긋나는 경우가 있었다).
3. 그래서 **2026-09-22부로 회의실·회의실 화면공유는 예외 없이 항상 LiveKit SFU를 쓰도록 고정했다.** 관리자나 발표자가 전송 방식을 고민할 필요가 없다 — 정원(시청 가능 인원)만 방 설정에서 관리하면 된다. 방 커스텀 스튜디오와 화면공유 실행 화면의 SFU/P2P 선택 UI는 제거했다.

### 4.3 P2P를 완전히 없앤 이유 (2026-09-26)
예전에는 1:1 화면공유, 회의 창 마이크·카메라, 근접 음성을 P2P로 보냈다. 실제 운영에서 다음 문제가 확인됐다.

1. **마이크·카메라를 껐다 켜면 상대에게 다시 전달되지 않았다.** 이미 멈춘 트랙이 전송 통로에 남아 새 트랙이 붙지 않았고, 카메라는 다시 켜도 상대 화면에 영상이 복원되지 않았다.
2. **소리가 들렸다 끊겼다를 반복했다.** 음량이 회의 참여 여부가 아니라 아바타 위치로 계산됐다.
3. **사무실 접속자 전원과 연결했다.** 회의 참가자가 아니어도 음성·영상 데이터가 PC까지 도착했고, 받는 쪽에서 음량만 0으로 줄였다. 연결 과정에서 각 PC의 IP도 다른 사용자에게 노출됐다.
4. **외부망 사용자끼리는 연결이 잘 안 됐다.** 중계(TURN)가 없어 재택·해외 접속자에게는 사실상 동작하지 않았다.
5. **인원이 늘면 감당하지 못했다.** 10명이 카메라를 켜면 각자 9번 인코딩하고 15~20Mbps를 업로드해야 했다.

LiveKit으로 통일하면 이 문제가 구조적으로 사라진다. 각자 한 번만 올리고, 서버가 방 단위로 받을 사람을 정하며, 외부망은 LiveKit의 ICE/TCP·TURN 경로를 쓴다. 보안 검토에서도 "모든 미디어는 서버가 발급한 토큰으로만 들어오는 방에서 흐른다"고 명확히 설명할 수 있다.

### 4.3.1 1:1 화면공유·1:1 통화 — 두 사람 전용 LiveKit 방
- 서버(`POST /api/direct-media/:peerId/livekit-token`)가 **로그인한 두 사람이 모두 접속 중이고 같은 건물인지** 확인한다. 그런 다음 두 사용자 ID로 방 이름(`vo-direct-<해시>`)을 계산한다. 제3자는 이 방의 토큰을 받을 수 없다.
- 한 방에서 **화면공유 · 마이크 · 카메라를 각각 따로 켜고 끈다.** 통화 중에 화면공유를 켜거나 꺼도 통화는 끊기지 않고, 통화를 끝내도 진행 중인 화면공유는 유지된다.
- 통화 요청·수락·거절·취소·종료는 WebSocket `direct_call` 신호로 주고받는다. 서버는 같은 건물 사용자끼리만 중계하고, 상대가 없으면 "부재", 회의·통화 중이면 "통화 중"으로 응답한다. 30초 동안 응답이 없으면 자동 취소된다.
- 마이크·카메라는 통화가 수락된 동안만 발행·수신한다. 통화 전에 켜 둔 머리 위 카메라는 통화 방으로 옮겨진다.

### 4.3.2 회의 창(크게보기) 마이크·카메라 — 회의실 방에 합류
- 회의 창을 열면 같은 회의실 LiveKit 방에 `meeting` 역할로 접속한다. 위치와 관계없이 벽 스크린을 멀리서 클릭하거나 하단 미리보기를 확대해도 바로 참여한다.
- 참가자 타일에는 `meeting`·`presenter` 역할인 사람만 표시한다. 3D 스크린만 보는 `attendee`와 나 자신(다른 창)은 제외한다.
- 참가자 마이크·카메라는 **회의 창이 열려 있는 동안만** 받는다. 회의 창을 닫은 발표자나 3D 스크린만 보는 사람은 회의 음성을 받지 않는다.
- 역할이 바뀌면(회의 중 화면공유 시작·종료) 재접속하는데, 이때 켜 두었던 마이크·카메라를 자동으로 다시 발행한다.
- LiveKit에 연결할 수 없으면 회의 창 하단에 안내하고 마이크·카메라 켜기를 막는다. "켜진 척"하지 않는다.

### 4.3.3 방 안 근처 대화와 머리 위 카메라 — 방별 LiveKit 방
- 방마다 LiveKit 방(`vo-near-<해시>`)이 하나씩 있다. 방이 다르면 LiveKit 방이 달라서, 다른 방·다른 층의 소리와 영상은 서버에서부터 섞이지 않는다.
- 서버(`POST /api/proximity-voice/livekit-token`)는 WebSocket으로 알고 있는 **사용자의 현재 방**과 요청한 방이 같을 때만 토큰을 발급한다. 방·층을 옮기거나 접속이 끊기면 이전 방에서 강제 퇴장시킨다.
- **음성 거리 규칙:** 2.5m까지 선명, 2.5~4m 점점 작게, 4m 밖 무음. 5m 안에 들어오면 수신을 시작하고 6.5m 밖으로 나가면 끊는다. iPhone은 `<audio>.volume`을 무시하므로 LiveKit `webAudioMix`와 `setVolume`으로 음량을 조절한다.
- **머리 위 카메라:** 같은 방 사람 모두가 받으며 근처 대화 설정과 무관하게 동작한다. 작은 칸에는 `adaptiveStream`으로 낮은 화질만 받는다.
- **관리자 설정:** 관리자 콘솔 "방별 시설 관리"에서 근처 음성 대화를 건물 전체 ON/OFF(기본 꺼짐), 방별 ON/OFF로 정한다(`GET/POST /api/proximity-voice/settings`, SQLite `proximity_voice_settings`). 끄면 서버가 LiveKit 방을 닫고 이후 토큰에서 마이크 권한을 뺀다. 클라이언트는 설정 정보나 서버 토큰 중 하나라도 음성을 막으면 즉시 마이크를 끈다. 카메라 전용 연결은 유지한다.
- **화면 표시:** 말하는 사람 발밑의 초록 링(들리지 않으면 흐린 남색), 내 주변의 2.5m/4m 범위 원, 왼쪽 아래 근처 대화 패널(4m 이내 사람·말하는 중·개인별 음소거), 머리 위 🎙️ 음파 표시, 회의 참여자의 "🎥 회의 중" 배지.

### 4.3.4 음성 채널은 하나만 — 회의 > 1:1 통화 > 근처 대화
- `audioChannelManager`가 "내 마이크가 지금 어디로 가는가"를 정하는 유일한 곳이다. HUD 마이크 버튼, M 단축키, 회의 창 버튼, 통화 카드가 모두 여기를 거친다.
- 회의 창을 열면 근처 대화 연결을 끊고, 켜 두었던 마이크를 회의로 옮긴다. 회의 창을 닫으면 마이크를 끄고(주변에 목소리가 새지 않도록) 근처 대화로 돌아온다.
- 1:1 통화가 시작되면 근처 대화에서 빠지고, 끝나면 마이크·카메라를 끈 채 돌아온다. 통화 중에 회의를 열면 확인창이 뜬다.
- 회의 창을 팝아웃으로 분리하면, 팝아웃이 닫힐 때까지 메인 창이 근처 대화에 들어가지 않는다. 팝아웃 창 자체는 근처 대화·통화 신호를 처리하지 않는다.
- 로그아웃하면 모든 채널을 정리하고, 서버가 그 세션의 WebSocket을 닫아 즉시 퇴장 처리한다.

### 4.3.5 알려진 한계
- LiveKit 토큰은 "받을 수 있는 트랙 종류"를 제한하지 못한다. 그래서 같은 회의실 방에 3D 스크린만 보려고 접속한 사람이 회의 음성을 받지 않는 것, 같은 방 안에서 5m 밖 음성을 받지 않는 것은 클라이언트 구독 설정으로 보장된다. 서버 수준 격리가 필요하면 "화면 시청 방"과 "회의 방"을 분리해야 한다.
- 스피커로 들으면 브라우저 에코 제거 때문에 두 사람이 동시에 말할 때 한쪽 목소리가 줄어들 수 있다. 헤드셋 사용을 권장한다.

### 4.4 회의실 화면공유의 실제 연결 경로
1. 발표자가 화면 공유를 시작하면 서버(`POST /api/shared-screen-rooms/:roomId/livekit-token`)에 발행(presenter) 역할의 토큰을 요청한다.
2. 서버는 그 방을 이미 다른 사람이 공유 중이거나 presenter 예약 중인지 확인해, 동시 시작 경합 시 나중 송출 요청을 거절한다. 시청 토큰과 송출 토큰은 별도 역할로 발급한다.
3. 시청자(팝업 뷰어, 3D 월드의 회의실 스크린 메시, 하단 PiP 미리보기)는 각각 독립적으로 같은 방을 attendee로 구독한다. 같은 방을 여러 화면 요소가 동시에 구독해도 실제 LiveKit 연결은 방마다 하나만 유지된다(참조 카운트 방식).
4. 방 하나 = LiveKit 방 하나로 매핑하되 미디어 방 이름에 고객·건물 템플릿·방 식별자를 함께 반영한다. 서로 다른 고객이나 건물에서 같은 방 ID를 사용해도 영상과 오디오가 섞이지 않는다.

## 5. 고객이 별도 LiveKit 계정을 만들어야 하는가

**절대 아닙니다.** 공급자가 제공하는 온프레미스 패키지에 Windows 네이티브 LiveKit SFU 서버가 완전히 내장되어 있으므로, 고객은 외부 클라우드 가입이나 유료 결제 없이 영구적으로 사내망에서 무료로 고성능 SFU 화면공유 및 회의를 이용할 수 있습니다.

고객사의 보안 정책상 외부 LiveKit Cloud나 중앙 미디어 인프라를 연동하고자 하는 경우에만 환경변수(`LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`)를 오버라이드하여 외부 서버로 우회 연결할 수 있습니다.

## 6. Docker Compose 구성 (Linux 환경 및 대규모 분산 클러스터링 옵션)

Windows 온프레미스 서버 환경에서는 앞서 설명한 **Windows 바이너리 번들 방식**을 권장하며, Linux 서버 배포나 수천 명 단위 분산 클러스터링을 구성할 때 Docker Compose를 활용할 수 있습니다.

- `redis`: LiveKit 상태/분산 조정용 Redis 7
- `livekit`: `livekit/livekit-server:v1.13.6` 기본 태그

기본 포트는 다음과 같다.

| 용도 | 포트 |
| --- | --- |
| Signal/WebSocket | TCP 7880 |
| RTC TCP fallback | TCP 7881 |
| TURN UDP | UDP 3478 |
| WebRTC media | UDP 50000–50300 |

일반 회의실보다 큰 타운홀을 수용하기 위해 LiveKit room의 내부 상한은 100으로 두며, 실제 서비스 한도는 애플리케이션 라이선스/세션 정책이 결정한다.

## 7. Docker 환경변수 설정 (고급 옵션)

`deploy/docker.env.example`를 `deploy/docker.env`로 복사하고 고객별 값으로 수정한다.

```dotenv
# 브라우저가 연결할 공개 또는 사내 TLS 주소
LIVEKIT_PUBLIC_URL=wss://meet.customer.example
# 컨테이너 내부 제어 API 주소. 브라우저에 노출하지 않는다.
LIVEKIT_API_URL=http://livekit:7880
LIVEKIT_API_KEY=customer-unique-key
LIVEKIT_API_SECRET=long-random-secret-at-least-32-characters
LIVEKIT_TOKEN_TTL_SECONDS=600
LIVEKIT_IMAGE_TAG=v1.13.6

# NAT/공인망 서버면 true, 사내 LAN 전용이면 보통 false
LIVEKIT_USE_EXTERNAL_IP=false
LIVEKIT_SIGNAL_PORT=7880
LIVEKIT_RTC_TCP_PORT=7881
LIVEKIT_TURN_UDP_PORT=3478
LIVEKIT_RTC_UDP_PORT_START=50000
LIVEKIT_RTC_UDP_PORT_END=50300
```

Docker Compose 미디어 구성에서는 `LIVEKIT_API_KEY`와 `LIVEKIT_API_SECRET`이 모두 필수이며, 하나라도 비어 있으면 구성 단계에서 실패합니다. Windows 번들 모드는 두 환경변수를 모두 생략할 수 있으며, 그 경우에만 첫 실행 시 설치 전용 키를 자동 생성하고 내부 LiveKit Standalone 바이너리를 `ws://[IP]:7880`으로 기동합니다. `LIVEKIT_PUBLIC_URL`은 외부 HTTPS/WSS 경로를 사용할 때 별도로 설정합니다.

## 9. 네트워크·보안 운영

- 외부 접속에는 TLS가 필수다. `wss://` 주소와 인증서, DNS를 먼저 준비한다.
- 방화벽/NAT에서 TCP 7880, TCP 7881, UDP 3478, UDP 50000–50300을 고객 네트워크 구조에 맞게 개방한다.
- 대칭 NAT·엄격한 기업망에서는 TURN relay와 실제 외부망 브라우저 검증이 필요하다.
- `LIVEKIT_API_SECRET`은 Git, 로그, 프론트엔드 번들, 고객 일반 관리자 권한에서 제외한다.
- Docker image tag는 운영에서 `latest`가 아닌 검증된 고정 버전을 사용한다.
- 미디어 서버는 CPU, 메모리, 업링크 대역폭, packet loss, TURN 사용률을 모니터링한다. 100명 타운홀은 사전 부하 시험 없이 보장하지 않는다.

## 11. 2026-09-23 갱신 — HTTPS 접속 시 화면공유 100% 실패하던 문제(mixed content) 수정, 거래처별 고정 도메인과의 연동

**증상**: Cloudflare 터널(HTTPS)로 접속한 페이지에서 화면공유를 시작하면 항상 "room connection has timed out (signal)"로 실패. 브라우저 콘솔에 `Mixed Content: ...loaded over HTTPS, but attempted to connect to the insecure WebSocket endpoint 'ws://...:7880/...'` 오류.

**원인**: 브라우저는 HTTPS 페이지에서 암호화 안 된 `ws://` WebSocket 연결을 정책적으로 완전히 차단한다(mixed content). 그런데 `server/index.js`의 `getDefaultLiveKitClientUrl()`은 이전(2026-09-22 이전)에 겪었던 다른 문제 — 로컬(`http://`) 접속에서 `wss://`로 잘못 승격시켜 TLS 인증서 없는 번들 LiveKit에 핸드셰이크가 실패하던 문제 — 를 고치면서 항상 `ws://`만 반환하도록 바꿔놨었다. 이게 이번엔 HTTPS 케이스를 깨뜨렸다: `http://` 접속엔 `ws://`가 맞고, `https://` 접속엔 `wss://`가 필수라 **접속 방식에 따라 분기해야만** 둘 다 동작한다.

**수정**:
1. 요청 헤더(`x-forwarded-proto` 등)로 HTTPS 접속인지 감지해서 분기 부활.
2. 번들 LiveKit 자체는 TLS 인증서가 없어서 `wss://같은호스트:7880`을 그대로 시도하면 TLS 핸드셰이크가 실패한다 — 그래서 메인 앱 터널과는 별개로 **LiveKit(7880) 전용 터널 호스트를 하나 더** 띄우고, 그 호스트가 Cloudflare 엣지에서 TLS를 대신 처리하도록 함. `livekit-tunnel.url` 파일에 그 호스트를 기록해두고 `getDefaultLiveKitClientUrl()`이 HTTPS 요청일 때 그 파일을 읽어 `wss://`로 반환.
3. 임시(Quick Tunnel)·온디맨드(`scripts/ServerTrayApp.cs`) 양쪽 모두 LiveKit 전용 짝 터널을 추가로 띄우도록 수정.

**2026-09-23 후속 — 거래처별 고정 도메인(Named Tunnel) 체계로 흡수됨**: 위 "LiveKit 전용 터널 호스트"는 원래 매번 랜덤 주소였는데, 거래처별 고정 서브도메인 시스템(`mdfile/1. Cloudflare_통합관리포털_배포및운영가이드_2026-09-24.md` 참고)이 만들어지면서 라이선스에 포함된 고정 미디어 호스트(`고객슬러그-media.calamus.ai.kr`)가 있으면 그 주소가 최우선으로 쓰인다. 운영 모드에서는 서명된 고정 도메인과 프로비저닝 정보가 일치해야 하며, Quick Tunnel은 초기 설정·장애 진단용 데모 흐름에서만 사용한다.

**검증**: 유진IT 거래처의 고정 도메인(`https://yujinit.calamus.ai.kr`)으로 실제 접속해 화면공유가 mixed-content 오류 없이 발행되는지 확인 완료(2026-09-23).

## 12. 2026-09-24 갱신 — 외부망 경로 진단과 TURN 구성

Cloudflare Tunnel을 통한 `wss://` 연결 성공은 LiveKit 시그널링 성공만 의미한다. 실제 영상·음성은 ICE/UDP, ICE/TCP 또는 TURN relay 중 하나로 별도 연결되어야 한다. 따라서 앱/미디어 고정 도메인만 등록한 상태를 외부 화면공유 완료 상태로 판단하지 않는다.

관리자 콘솔의 `서버 상태 → 외부망 WebRTC 경로 진단`은 다음을 각각 표시한다.

- LiveKit 로컬 신호 포트 TCP 7880
- ICE/TCP 대체 포트 TCP 7881
- 라이선스에 서명된 미디어 호스트의 DNS와 HTTPS/WSS 도달성
- RTC UDP 50000~50200, TURN/UDP, TURN/TLS 구성
- 외부 PC·모바일 실기 시험 필요 여부

Windows 내장 LiveKit에서 TURN/UDP를 사용할 때는 서버 실행 전 `LIVEKIT_TURN_ENABLED=true`, `LIVEKIT_TURN_UDP_PORT=3478`을 설정한다. TURN/TLS는 `LIVEKIT_TURN_DOMAIN`, `LIVEKIT_TURN_TLS_PORT`, `LIVEKIT_TURN_CERT_FILE`, `LIVEKIT_TURN_KEY_FILE`을 모두 설정해야 생성된다. 인증서는 공인 CA 서명이 필요하며 TURN 도메인과 일치해야 한다.

운영 선택지는 다음 둘 중 하나다.

1. 공인 IP/NAT 포트포워딩: `LIVEKIT_USE_EXTERNAL_IP=true`, TCP 7881, UDP 50000~50200(필요 시 TURN/UDP 3478)을 외부에서 LiveKit 서버로 전달한다.
2. TURN/TLS: 별도 TURN 도메인과 공인 인증서를 구성하고 TCP 443 또는 배포 구조에 맞춘 TLS 포트를 L4로 LiveKit에 전달한다.

정식 운영 판정은 서로 다른 외부망의 PC와 모바일에서 발표·구독·오디오·재연결을 시험한 뒤에만 내린다.
