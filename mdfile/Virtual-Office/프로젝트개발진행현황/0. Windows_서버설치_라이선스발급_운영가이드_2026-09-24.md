## 2. Windows 설치 절차

1. Windows 10/11 또는 Windows Server의 서버 PC에서 설치 EXE를 관리자 권한으로 실행한다.
2. 기본 경로 `C:\Virtual_Office_Server`에 설치한다.
3. 설치가 끝나면 `VirtualOfficeServer.exe`를 실행한다. 포터블 Node.js와 SQLite 엔진이 포함되어 별도 Node 설치는 필요하지 않다. 내장 `livekit-server.exe`가 실행되며, 최초 실행 시 이 설치만의 LiveKit API key/secret과 `server/data/livekit/livekit.runtime.yaml`을 생성해 로컬 SFU를 자동 기동한다. 고정 키가 들어 있는 YAML은 설치 패키지에 포함되지 않는다.
4. Windows 방화벽에서 사내망 프로필의 TCP 3001 포트를 허용한다.
5. 서버 PC에서는 `http://localhost:3001`, 다른 사내 PC에서는 `http://서버IP:3001`으로 접속한다.

데이터베이스 위치는 `C:\Virtual_Office_Server\server\data\virtual_office.db`다. 운영 전에는 서버 중지 후 이 파일을 정기 백업하고, 복원 연습도 수행한다.

LiveKit 설치 자격 증명은 `C:\Virtual_Office_Server\server\data\livekit\credentials.json`에 저장된다. 이 파일과 같은 폴더의 런타임 YAML은 DB 백업과 별도로 접근 권한을 제한하고 외부에 전달하지 않는다.

## 3. 최초 관리자와 사원 로그인

### 운영 패키지

운영 패키지에는 고정 관리자 계정이 없다. 첫 실행 시 `server\data\bootstrap-token.txt`가 생성된다. 이 토큰으로 `/api/setup/admin`을 한 번 호출해 고객 관리자 계정을 만들고, 성공 후 토큰 파일은 폐기한다.

```powershell
$token = Get-Content 'C:\Virtual_Office_Server\server\data\bootstrap-token.txt' -Raw
$body = @{ id='admin'; email='admin@customer.example'; name='고객사 관리자'; password='10자_이상의_강한_비밀번호' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://localhost:3001/api/setup/admin' -ContentType 'application/json' -Headers @{ 'X-Bootstrap-Token' = $token.Trim() } -Body $body
```

그 다음 관리자 센터에서 팀, 사원, 조직도를 등록한다. 고객 사용자 관리자는 사원과 팀을 운영할 수 있지만, 계약으로 고정된 건물 템플릿·층수·방 구성은 변경할 수 없다.

`server/index.js`는 `VO_REQUIRE_LICENSE=0`으로 명시적으로 끄지 않는 한 운영 프로파일에서 항상 라이선스를 강제한다(2026-09-21 수정, 8.2절 참고) — 라이선스가 `active`/`grace` 상태가 아니면 "3D 오피스 입장" 버튼이 "🔒 라이선스 등록 필요"로 바뀐다.

### 데모 패키지

데모 DB에는 두 종류의 자가 복구 관리자 계정이 매 부팅마다 자동으로 등록/복구된다(둘 다 데모 프로파일 전용, 운영 설치와는 무관):

| 계정 | 용도 |
|---|---|
| `yujinit2005@gmail.com` / `officeadmin123!@#` | **마스터 개발자** 계정. 로그인 화면 [관리자 로그인] 탭의 `[🛠️ 마스터 개발자 입력]` 버튼으로 원클릭 로그인 가능. 건물/방 커스텀 스튜디오, 계약·프리셋 관리 등 공급자 전용 기능에 접근. |
| `officeadmin` / `admin123!@#` | **고객사 관리자 데모 계정**(id `admin-master`, 2026-09-22 복구). "일반 고객사 관리자라면 이렇게 보인다"를 데모에서 바로 확인하기 위한 계정 — 사원/부서 관리 화면까지만 접근하고 공급자 전용 기능은 없다. |

사원 선택 로그인 공용 비밀번호는 `1234`이며, 데모 시연용으로만 사용한다. 실제 고객 운영에서는 사원별 초기 비밀번호를 배포하고 최초 로그인 시 변경하도록 운영한다.

첫 로그인 화면에서 사원 목록이 비어 있으면 서버가 완전히 기동된 뒤 새로고침한다. 로그인 모달은 로그인 전에도 SQLite 사원 목록을 동기화하도록 구현되어 있다. 계속 비어 있으면 `/api/users`와 서버 로그, DB 파일 존재 여부를 확인한다.

> **참고**: `officeadmin` 계정은 한때 제거됐다가(가짜 하드코딩 데이터 정리 과정에서 함께 삭제) 2026-09-22에 자가 복구 패턴으로 다시 추가됐다. 데모 환경에는 이제 로그인 가능한 계정이 마스터 개발자 하나만 남는 일이 없도록, 두 계정 모두 `seedInitialData()`가 부팅마다 존재를 확인하고 없으면 재생성한다.

## 4. 건물 템플릿과 Room 단위 구조

### 4.1 8대 업종 템플릿 (2026-09-18 확정)

설치형 **데모 모드에서만** 대시보드에서 여러 업종 템플릿을 선택해 확인할 수 있다. 층수는 고정이 아니라 스튜디오에서 1층~N층까지 자유롭게 증축·구성하는 가변 요소다.

1. `startup-2f` (스타트업) — 스크럼룸, 집중 업무실, 루프탑
2. `company-standard` (일반회사·중소기업) — 부서별 업무공간, 대형 컨퍼런스룸, 임원 집무실
3. `rnd-center` (연구소·R&D 센터)
4. `finance-global` (금융·글로벌)
5. `public-agency` (공공기관·지자체)
6. `school` (학교·교육기관)
7. `custom-rooftop` (맞춤 사옥 + 옥상정원)
8. `custom` (자유 맞춤설계)

이 선택은 해당 브라우저의 데모 미리보기이며 다른 사용자 DB나 try에 영향을 주지 않는다. **2026-09-22부로 템플릿을 전환해도 표시되는 팀/사원은 항상 실제 DB에 등록된 레코드다** — 과거에는 "3D 오피스 입장" 버튼을 누를 때마다 클라이언트 전용 가짜 직원 프리셋으로 화면을 덮어썼으나 이 로직을 완전히 제거했다(10장 참고). 운영 설치본에서 건물 구조 변경은 공급자/개발자 권한과 계약 변경 절차를 거친다.

### 4.2 방(Room) 단위로 통합된 협업 기능 (2026-09-21)

과거에는 채팅·화상회의·화면공유·화이트보드가 서로 다른 방 식별 체계를 썼지만(고정 5개 회의실 이름, 화면공유 전용 슬롯 등), 이제 전부 **방의 실제 `room.id`를 공유**한다:

- 서버가 라이선스의 `customFloors[].rooms[]`(운영) 또는 활성 건물 프리셋의 `roomTemplates`(데모)를 **직접 읽어** 팀·화면공유·화이트보드 마스터 레코드를 자동 생성한다(`resolveRoomsForTemplate()` + `generateFacilitiesForTemplate()`).
- 방마다 사람이 읽는 직렬 코드가 자동 채번된다: `RM-{템플릿코드}-{층}{순번}` (예: `RM-STU-101`). 재생성해도 이미 배정된 코드는 유지된다.
- 관리자 콘솔에서 방별로 화상회의 스크린/화이트보드를 개별로 켜고 끌 수 있는 시설 관리 CRUD가 추가됐다(`GET/POST /api/room-facilities`, `DELETE /api/room-screens/:id`, `DELETE /api/room-whiteboards/:id`).
- 라이선스의 `regularMeetingRooms`는 "고정 5개 이름 중 앞 N개 허용"이 아니라 "**동시에 열려있는 회의 세션 개수 상한**"(`maxConcurrentRegularMeetings`)으로 재해석된다 — 계약서 필드 자체는 변경 없음.

팀·좌석 운영 화면에서는 팀 이름, 팀 배치 층, 좌석 수를 조절할 수 있다. 팀의 층을 바꾸면 소속 사원도 같은 층으로 이동한다. 좌석 수는 현재 소속 인원보다 작게 설정할 수 없다(최솟값 0은 허용). 사무실 층의 일반 좌석은 2인 책상 묶음으로, 두 사람이 서로 마주 보도록 책상·의자·아바타 좌표가 동기화되어 있다.

### 4.3 회의실 화면공유는 항상 LiveKit SFU (2026-09-22)

회의실 화면공유는 이제 예외 없이 로컬 내장 LiveKit SFU를 거친다. 과거 UI에는 "P2P 직결/SFU" 선택지가 있었지만 실제 전송과 일치하지 않았고, 2026-09-22에 실제 SFU 연동으로 교체했다. 2026-09-25~26부터는 1:1 채팅 화면공유·1:1 음성/영상 통화(두 사람 전용 방), 회의 창 마이크·카메라(회의실 방), 방 안 근처 대화·머리 위 카메라(방별 방)까지 **모든 음성·영상이 LiveKit SFU**를 거친다. 사용자 간 P2P 연결은 없다. 자세한 현재 구조는 `2. LiveKit_SFU_연동_구현및운영가이드_2026-09-24.md` 4장과 `화상회의_근처대화_1대1통화_통합테스트시나리오_2026-09-26.md`를 참고한다. 따라서 LiveKit 포트(7880/7881/UDP 50000~50200)와 미디어 주소가 막히면 회의·1:1 통화·근처 대화·카메라가 함께 영향을 받는다. 외부망(고객사 밖) 송출은 TLS, 방화벽/NAT, TURN, 공개 URL을 고객망에 맞게 별도 설정하고 실기기 검증이 필요하다(11장 참고).

### 4.4 방별 회의 예약과 팀별 임박 알림 (2026-09-28)

- 일반 방 회의는 실제 화상회의 스크린이 활성화된 방만 예약할 수 있다. 외부 게스트·발표자 관리가 필요한 행사는 타운홀 예약을 사용한다.
- 시작과 종료는 날짜가 포함된 절대 시각으로 저장하며, 종료가 시작보다 빠르거나 시작 시각이 이미 지났거나 동일 방의 다른 일정과 겹치면 서버가 거부한다.
- 참석 대상은 전사 또는 특정 팀이다. 팀 전용 회의는 해당 팀·예약자·관리자만 입장할 수 있다.
- 예약 생성은 `meeting.schedule`, 수정·삭제는 예약자 또는 관리자 권한으로 서버에서 검증한다.
- 대시보드와 3D HUD는 같은 일정 상태 계산을 사용한다. 30분 이내는 임박, 10분 이내는 강조, 시작~종료 사이는 진행 중으로 표시한다.
- `meeting_schedule_changed` WebSocket 이벤트가 생성·수정·삭제를 접속자에게 전달한다. 역방향 프록시와 방화벽은 기존 업무 WebSocket 연결을 허용해야 한다.
- 운영 DB의 기존 `meetings` 테이블은 시작 시 호환 마이그레이션된다. 배포 전 DB 백업 후 `npm run test:meeting-schedule`로 날짜·팀·중복·권한·실시간 갱신을 확인한다.

## 5. 핵심 아키텍처: 계약에 건물 JSON을 결합해 위변조 불가능하게 만든다

이 솔루션은 온프레미스 컨셉이라 **클라우드(Cloudflare)에는 계약 정보 외에는 아무것도 보관하지 않는다.** 그 전제 위에서, 거래처에 발급하는 라이선스 파일 자체에 그 거래처의 건물 구성(JSON)을 통째로 서명해 넣어 — 고객이 라이선스 파일이나 건물 구성을 임의로 바꿀 수 없게 만드는 것이 이 아키텍처의 핵심이다.

- 공급자 포털에서 계약을 만들 때, 스튜디오에 저장해 둔 건물 프리셋(샘플 업종 템플릿 **또는** 거래처 전용 프리셋)을 하나 골라 계약에 잠근다.
- 라이선스 발급(`functions/api/manage/licenses/issue.js`) 시 그 계약에 묶인 건물 프로필(`contract_building_profiles.profile_json`)을 payload에 포함해 Ed25519로 서명한다.
- 서명된 payload는 로컬 서버가 검증하며(`server/license.js`의 `getLicenseStatus`), 서명이 깨지면 전체가 거부된다 — 건물 구성만 따로 바꿔치기할 수 없다.

### 5.1 거래처별 건물 프리셋 — 샘플과 분리 (2026-09-21)

기존에는 "업종 템플릿"(기본 5층 사무실, 스타트업 2층, 학교 등 샘플) 몇 종만 있었고, 계약마다 조금씩 다른 실제 고객 요구사항을 반영할 방법이 없었다.

- **D1 `building_presets` 테이블**을 15컬럼 표준 스키마로 재정비(`functions/_lib/building-presets.js`). `templateCode`(공용 업종 템플릿) 또는 `customerCode`(거래처 전용)로 구분해서 저장한다.
- 스튜디오(`RoomCustomStudioModal.tsx`)에 **"거래처별 템플릿" 탭**을 추가: 실제 거래처를 선택하고, 저장된 최신 버전을 불러오거나 새로 시작해서 편집·저장할 수 있다. 샘플 업종 템플릿을 편집해도 공용 샘플이 오염되지 않는다.
- 계약 생성 화면(`PortalWorkflows.tsx`의 `ContractWorkflow`)에서 "업종 템플릿" 콤보를 제거했다 — 저장된 JSON을 그대로 읽어오면 되므로 별도 업종 선택 단계가 불필요하다. 공용 프리셋/거래처 프리셋을 하나의 "계약 건물셋" 콤보에서 고르고, 버전이 여러 개 저장돼 있어도 **최신(active) 버전 하나만** 노출한다(`pickActiveOrLatestPresets()`).
- 계약 삭제 기능 추가(`functions/api/manage/contracts/[id].js`의 `onRequestDelete`) — `draft` 상태이고 결제·라이선스가 하나도 없는 계약만 삭제 가능.

DB 스키마는 두 D1(`calamus-virtual-office`, `virtual-office-demo-db`)과 로컬 SQLite 세 곳 모두 `migrations/0007_building_presets_baseline.sql` 기준으로 동일하게 유지한다 — **한 곳만 스키마를 바꾸지 않는다.**

## 6. 라이선스 발급과 적용

라이선스는 서버별 공개키와 설치 인스턴스 정보에 묶인다.

1. 고객 설치 서버에서 `.calamus-request`를 생성한다.
2. 공급자 발급 PC(포털)에서 활성 계약 payload를 작성한다. 필수 범위는 유효기간, 동시 사용자, 등록 사용자, 계약 건물셋(업종 템플릿 또는 거래처 전용 프리셋), 회의/타운홀 옵션이다. 동시 화면공유 상한은 별도 고정 숫자가 아니라 서명된 건물셋의 화면 스크린 수에서 계산한다.
3. 공급자 개인키로 `.calamus-license`를 서명한다(발급 직후 공개키로 자체 검증 — 7장 참고).
4. 고객 서버 관리자에게 서명된 라이선스 파일만 전달한다.
5. 고객 서버에서 등록 후 `GET /api/license/status`로 검증한다.
6. 정상 검증 뒤 운영 프로파일은 라이선스가 자동으로 강제 적용된다(`VO_REQUIRE_LICENSE=0`으로 명시적으로 끄지 않는 한).

개인 발급키는 고객 서버, 설치 패키지, Git, 이메일에 넣지 않는다. 키 유출 시 새 키쌍으로 재발급하고 공개키를 포함한 이후 배포 패키지를 교체한다.

예시 payload:

```json
{
  "licenseId": "LIC-CUSTOMER-001-2026",
  "customerId": "CUSTOMER-001",
  "validFrom": "2026-09-17T00:00:00.000Z",
  "validUntil": "2027-09-16T23:59:59.999Z",
  "maxConcurrentUsers": 100,
  "maxRegisteredUsers": 200,
  "maxConcurrentSharedScreens": 30,
  "townHallEnabled": true,
  "maxTownHallParticipants": 100,
  "maxTownHallPresenters": 4
}
```

학교 계약은 학년·반 수, 반별 인원, 교실/공용공간 구성과 화면 스크린이 포함된 건물 프로필을 payload에 고정한다. 학교도 임의의 5건/30건 상한을 쓰지 않고, 서명된 건물의 실제 화면 스크린 수를 최대 동시 송출 수로 사용한다.

**타운홀 세부 조건(2026-09-22 추가 준비)**: 최상위 `townHallEnabled`/`maxTownHallParticipants`/`maxTownHallPresenters`는 기존부터 쓰이고 있었다. 여기에 더해 `buildingProfile.townHall = { enabled, logoUrl }` 형태로 건물 프로필 안에도 타운홀 조건을 실을 수 있도록 `normalizeBuildingProfile()`(양쪽 파일 동일하게) 준비해 뒀다 — 회사명은 별도 필드 없이 기존 `customerName`을 그대로 재사용한다. 다만 **공급자 포털의 라이선스 발급 화면에는 아직 이 값을 입력하는 UI가 없다**(서버·스튜디오 쪽만 이번에 준비됨) — 포털에서 이 필드를 채워 넣는 입력창을 만드는 작업은 별도로 남아있다.

### 6.1 ⚠️ 절대 한쪽만 수정하면 안 되는 코드

- `functions/_lib/license-crypto.js`와 `server/license.js`의 `canonicalize()`는 **바이트 단위로 동일한 출력**을 내야 한다. 한쪽만 수정하면 서명 불일치가 발생해 모든 고객 서버의 라이선스가 무효화된다.
- `server/license-public.pem`(Ed25519 공개키)을 덮어쓰면 기존 라이선스가 전부 무효가 된다.
- `normalizeBuildingProfile()`은 `functions/_lib/building-templates.js`와 `server/license.js` 두 곳에 있다. `customFloors` → `rooms` 매핑에서 보존하는 필드 목록(`id`, `name`, `type`, `moduleType`, `capacity`, `furnitureLayout`, `whiteboard`, `dimensions`, `placedItems`, `roomCode`, `category`, `screenSlot`)이 반드시 동일해야 한다.

## 7. Cloudflare Pages 시크릿 운영 절차 (라이선스 서명키)

> 2026-09-21에 **실제로 겪은 장애**(고객 서버에서 반복적으로 `signature_invalid`)의 근본 원인이자 재발 방지 절차. 상세 사고 경위는 8장 참고.

Cloudflare Pages는 환경변수/시크릿을 **배포 시점에 고정(bake)** 한다. 대시보드에서 시크릿을 변경해도 이미 활성화된 배포에는 반영되지 않으며, 반드시 **새 배포**가 필요하다.

### 7.1 시크릿을 바꿀 때의 표준 절차

1. Cloudflare Pages 대시보드 → Settings → Environment variables → Production에서 시크릿 변경
2. 즉시 **새 배포 트리거**: `git push`로 커밋을 올리거나, 대시보드에서 최신 배포의 "Retry deployment" 클릭
3. 배포 성공 후 **커스텀 도메인 alias 전환 대기**: 배포가 `success`로 끝나도 커스텀 도메인(`worknexus.calamus.ai.kr`)이 새 배포를 가리키기까지 수 분 걸릴 수 있음
4. 전환 확인: 발급 응답의 `_signingKeyFingerprint` 값을 로컬 키의 핑거프린트(`node scripts/fingerprint-env-key.mjs`)와 비교
5. 일치를 확인한 뒤에만 라이선스 발급

### 7.2 안전한 발급 워크플로

- 시크릿을 변경한 직후에는 **커스텀 도메인이 아닌 최신 배포의 고정 URL**(`https://<배포해시>.virtual-office-1pq.pages.dev/manage`)에서 발급하는 것이 가장 안전하다.
- `LICENSE_SIGNING_PUBLIC_KEY`는 **필수 Secret**이다(2026-09-21부로 조건부 검증에서 필수 검증으로 변경). 미설정 시 발급 API가 `license_verification_key_not_configured`로 즉시 거부한다. 설정되어 있으면 발급 직후 그 공개키로 자체 검증하며, 실패하면 `self_verification_failed`로 파일 생성 자체를 막는다 — 시크릿 불일치 시 잘못된 라이선스가 아예 생성되지 않는다.
- `LICENSE_SIGNING_PUBLIC_KEY`는 비밀 값은 아니지만(공개키이므로), **`LICENSE_SIGNING_PRIVATE_KEY`와 같은 방식(Secret)으로 등록**해야 한다 — 일반 환경변수와 시크릿의 반영 타이밍이 어긋나면 두 값이 서로 다른 배포에서 읽혀 자체 검증이 무의미해질 수 있기 때문이다. Production과 Preview 환경 모두에 등록한다.
- 만약 이미 잘못된 키로 서명된 라이선스가 발급되었다면, `scripts/re-sign-license.mjs`로 즉시 재서명하여 복구 가능(8.3절 참고).

### 7.3 진단 스크립트

| 스크립트 | 용도 |
|---|---|
| `scripts/re-sign-license.mjs` | 잘못된 키로 서명된 라이선스를 로컬 개인키로 재서명 |
| `scripts/export-payload.mjs` | 발급된 `.calamus-license` 파일에서 payload만 추출 |
| `scripts/sign-payload-locally.mjs` | 추출된 payload를 로컬 개인키로 서명하여 비교 |
| `scripts/fingerprint-env-key.mjs` | `.env`의 현재 개인키 핑거프린트 출력 |

### 8.2 엔터프라이즈 로컬 설치본에서 라이선스 인증 전 3D 오피스 입장이 되던 문제 (2026-09-21, 해결)

- **원인**: Windows 배치 설치본이 `VO_REQUIRE_LICENSE` 환경변수를 아무도 설정하지 않았고, 서버 코드가 `=== '1'`일 때만 라이선스를 강제하는 **화이트리스트 방식**이었던 것. Docker 배포만 우연히 이 값을 명시적으로 넣어줘서 문제가 안 보였다.
- **수정**: `server/license.js`는 기본값을 뒤집어 `VO_REQUIRE_LICENSE=0`으로 명시적으로 끄지 않는 한 프로덕션은 항상 라이선스를 강제하도록 변경. `server/index.js`의 `/api/health`의 `license.required`도 배포 프로파일 기준으로 일치. 클라이언트(`App.tsx`, `useOfficeStore.ts`, `InternalHome.tsx`, `AdminManagementHub.tsx`)는 라이선스가 `active`/`grace`가 아니면 "3D 오피스 입장" 버튼이 "🔒 라이선스 등록 필요"로 바뀌고 클릭 시 라이선스 관리 화면으로 이동하도록 수정. `npm run package:production`으로 설치 패키지 재생성 완료.
- 부가로 공급자 관리 포털에 로그인/로그아웃 상태 표시(`/cdn-cgi/access/get-identity`, `/cdn-cgi/access/logout` 연동)도 함께 추가했다.

### 8.3 라이선스 서명 검증 실패(`signature_invalid`) — 근본 원인은 Cloudflare 시크릿 bake 타이밍 (2026-09-21, 해결)

**증상**: 공급자 포털에서 발급한 `.calamus-license`를 고객 서버(로컬 Windows 설치본)에 등록하면 반복적으로 `signature_invalid`로 실패.

**확정된 원인**: Cloudflare Pages의 시크릿(`LICENSE_SIGNING_PRIVATE_KEY`)이 **이전 배포에 고정(bake)된 상태**에서 발급이 일어났다. Ed25519는 결정적(deterministic) 서명이므로 같은 키+같은 메시지면 반드시 동일한 서명이 나온다. 실제 발급된 라이선스의 서명을 로컬 `.env` 개인키로 재서명해보니 완전히 다른 값이 나왔다 — **다른 키로 서명된 것이 100% 확실**했다(로컬 `.env` 키와 `license-public.pem`은 쌍이 정확히 일치함도 확인). Cloudflare Pages는 대시보드에서 시크릿을 변경해도 이미 활성화된 기존 배포에는 반영되지 않고, 새 배포(git push 또는 "Retry deployment") 후에도 커스텀 도메인의 production alias가 전환되기까지 수 분의 지연이 있을 수 있다 — 그 시간창에 발급하면 이전 키가 사용된다.

**즉시 해결**: `scripts/re-sign-license.mjs`로 잘못된 키로 서명된 라이선스 파일을 로컬 개인키로 재서명. 재서명된 파일은 전체 검증(서명·필수 필드·인스턴스 바인딩·유효기간)을 모두 통과하고 정상 등록 완료 — 향후 같은 문제가 재발하면 이 스크립트로 즉시 복구 가능.

**재발 방지**: 7장의 "필수 자체 검증 + `LICENSE_SIGNING_PUBLIC_KEY` Secret 등록" 절차를 도입해, 시크릿이 어긋난 상태에서는 발급 자체가 막히도록 했다.

### 8.4 스튜디오 거래처별 템플릿 편집/저장 오염 버그 (2026-09-21, 해결)

**증상**: 스튜디오에서 "거래처별 템플릿 · 유진IT"를 불러오면 일반 샘플("일반회사·중소기업") 방이 섞여 보이고, 탭 활성화 표시가 동시에 뜸. 유진IT용으로 저장하면 직전에 만지던 일반 샘플의 잔여 방까지 같이 저장됨(3층이어야 할 건물이 5층으로 저장된 사례).

**원인**: `useOfficeStore`의 편집용 라이브 드래프트 상태(`roomTemplates`, `vo_custom_room_templates`)가 `buildingTemplateCode`로만 구분되고 거래처(customerCode) 구분이 전혀 없는 **단일 전역 배열**이었다. D1 `building_presets` 테이블 자체는 처음부터 `customer_code`로 올바르게 분리돼 있었으므로(즉 DB에 남은 데이터나 실제 발급 흐름은 오염되지 않았음), 문제는 스튜디오 편집 화면 앞단에 국한됐다.

**수정**: `CustomRoomTemplate`에 `ownerScope` 필드 추가(`src/types/furnitureCatalog.ts`). `useOfficeStore`에 `roomStudioActiveCustomerScope` 상태를 추가하고 `loadBuildingPreset`(전체 배열 교체 → 같은 건물+같은 스코프만 교체하는 병합)·`applyRoomTemplatesToBuildingWorld`·`saveCategoryAsDefaultDemoSet`·`addBuildingFloor`·`addRoomTemplate`을 전부 이 스코프 기준으로 필터링/스탬핑하도록 수정. `RoomCustomStudioModal.tsx`의 방 목록·방번호 채번/일괄정리·JSON 불러오기·탭 활성화 표시도 전부 스코프 인식하도록 수정.

### 8.5 `virtual-office-demo-db`에 거래처 프리셋이 미러링되지 않던 문제 (2026-09-21, 해결)

**증상**: 유진IT 같은 실제 거래처 건물 프리셋이 `calamus-virtual-office`(SUPPLIER_DB)에만 저장되고 `virtual-office-demo-db`에는 없음.

**원인**: `functions/api/building-presets/*` 엔드포인트가 `context.env.SUPPLIER_DB`에만 쓰고 있었고, Pages Functions에는 `DEMO_DB` 바인딩 자체가 연결되어 있지 않았다.

**수정**: `functions/_lib/building-presets.js`에 `mirrorToDemoDb()` 헬퍼를 추가하고, 프리셋 저장/삭제/기본셋 리셋 엔드포인트 전부에서 SUPPLIER_DB 쓰기 직후 best-effort로 DEMO_DB에도 반영하도록 했다(DEMO_DB 저장 실패는 SUPPLIER_DB 쪽 응답을 막지 않음). **운영자가 직접 할 작업**: Cloudflare Pages 대시보드 → 해당 프로젝트 → Settings → Functions → D1 database bindings에서 `DEMO_DB` = `virtual-office-demo-db`를 Production/Preview 모두에 추가하고 재배포해야 실제로 미러링이 시작된다(바인딩이 없으면 조용히 아무것도 안 하고 SUPPLIER_DB 저장만 정상 진행됨, 에러 없음).

### 8.6 스튜디오 거래처별 템플릿 오염 버그 2차 재발 — 3D 미리보기 전역 캐시 경로 (2026-09-22, 해결)

**증상**: 8.4에서 고친 뒤에도 거래처(유진IT) 전용 건물셋을 편집·저장하거나 거래처 모드를 나가면, 같은 업종의 공용 샘플 탭(예: "스타트업")에 그 거래처의 방 구성이 다시 보임.

**원인**: 8.4의 수정은 영구 데이터 계층(`roomTemplates` 배열, DB의 `building_presets`)만 스코프별로 분리했다. 그런데 3D 미리보기에 실제로 쓰이는 **전역 캐시 객체 `DEMO_BUILDING_PLANS[템플릿코드]`**(스튜디오를 보는 모든 사용자가 공유)는 두 지점에서 여전히 스코프 구분 없이 덮어써지고 있었다: (1) `saveCategoryAsDefaultDemoSet()`이 "기본셋 저장" 시마다 이 캐시와 `localStorage`의 `vo_custom_demo_default_{category}` 키(앱 시작 시 그대로 로드됨)를 무조건 갱신, (2) `exitCustomerTemplateMode()`("✕ 거래처 모드 종료")가 스코프 플래그만 끄고 거래처 편집 중 반영해 뒀던 캐시를 공용 최종본으로 되돌리지 않음.

**수정**: `saveCategoryAsDefaultDemoSet()`의 캐시·localStorage 갱신을 `customerCode === 'COMMON'`일 때만 실행하도록 제한. `exitCustomerTemplateMode()`가 공용 모드로 돌아올 때 해당 업종의 COMMON 활성 버전을 서버에서 다시 불러와 캐시를 복구하도록 추가. 부가로 "빈 방으로 시작하기" 옵션과, 거래처 모드 중 업종 탭을 더 이상 함께 강조하지 않는 UI 변경도 함께 반영(자세한 내용은 `mdfile/0. 방_건물_커스텀스튜디오_프리셋_연동_및_계약연계_가이드.md` 8장 참고).

> ⚠️ 이 2차 버그로 인해 수정 전 세션에서 이미 오염된 브라우저 `localStorage`가 남아있다면, 수정 이후에도 새로고침 시 예전 값이 다시 로드될 수 있다. 여전히 공용 탭에 거래처 방이 보이면 `localStorage.removeItem('vo_custom_demo_default_{템플릿코드}')` 실행 후 새로고침이 필요하다.

### 8.7 서버가 두 번째 부팅(재시작)마다 죽는 치명적 크래시 — `no such column: building_code` (2026-09-22, 해결)

**증상**: 데모 패키지를 설치하고 서버를 재시작하면(트레이 앱 재기동, 수동 재실행, 같은 폴더에 재설치 등) 콘솔에 `ERR_SQLITE_ERROR: SQL logic error` / `no such column: building_code`가 뜨며 서버 프로세스가 죽는다. **패키징과 무관하게 이 저장소로 띄우는 모든 서버(로컬 `npm run dev` 포함)가 부팅 2회차부터 겪는 문제였다** — `VO_DATA_DIR`을 임시 폴더로 지정해 `initDatabase()`를 연속 실행해 재현·확인.

**원인**: `room_screens`/`room_whiteboards`를 `(template_code, room_id)` 복합 UNIQUE로 재구성하는 `rebuildTableWithNewUniqueness()`가 `building_code` 컬럼명을 참조하는 고정 `CREATE INDEX` 문을 실행하는데, 바로 다음 마이그레이션 단계(`RENAME COLUMN building_code TO template_code`)가 그 인덱스를 보존하지 않고 지워버렸다(코드 주석이 "RENAME COLUMN이 인덱스도 갱신해준다"고 잘못 가정). 그래서 2회차 부팅부터는 이미 `template_code`로 바뀐 테이블에, 여전히 `building_code`를 참조하는 낡은 인덱스 문으로 재생성을 시도하다가 오류로 프로세스 전체가 죽었다.

**수정**: 해당 인덱스 생성을 다른 무중단 마이그레이션과 동일하게 실패해도 부팅을 막지 않도록 `try/catch`로 감쌌다(인덱스는 조회 성능 최적화일 뿐 기능엔 영향 없음). `RENAME COLUMN` 직후 `template_code` 기준의 올바른 이름으로 인덱스를 다시 생성해 조회 성능도 복구했다. `initDatabase()`를 3회 연속 실행해 재발하지 않음을 확인.

> ⚠️ **이미 배포한(오늘 재생성한 것 포함) 이전 패키지로 한 번이라도 부팅한 설치본은 다음 재시작 때 이 오류를 만난다.** 이 수정을 반영해 패키지를 다시 만들어 재배포해야 한다 — 기존 설치 폴더에 새 패키지를 덮어 설치해도(`server/data/virtual_office.db`를 지우지 않아도) 이 코드 수정만으로 다음 부팅부터 정상 동작한다.

### 12.3.1 라이선스의 PC 귀속 기준

- 신규 인증요청파일(schema 2)은 Windows CIM의 시스템 UUID와 메인보드 일련번호를 정규화한 뒤 SHA-256으로 해시한 `machineFingerprintHash`를 포함합니다.
- 공급자가 이 요청을 발급하면 라이선스 schema 4에 해시가 서명되며, 실행 때마다 현재 PC의 해시와 비교합니다.
- BIOS/메인보드 원본 식별자는 고객 서버 밖으로 전송하지 않습니다. 일방향 SHA-256 결과만 인증요청파일에 포함됩니다.
- 기존 schema 2/3 라이선스는 하위 호환을 위해 기간 만료일까지 작동하지만 하드웨어 귀속이 없습니다. 보안이 중요한 운영 서버는 신규 요청으로 재발급합니다.
- 서명된 `validUntil`은 PC 복제 여부와 관계없이 계속 강제됩니다. 다만 구형 라이선스는 다른 PC 복제 방지가 불충분하므로 재발급이 필요합니다.

### 12.4 서명된 터널 무결성

- 라이선스 페이로드의 `networkBinding`은 터널 ID, 앱 호스트, 미디어 호스트를 포함합니다.
- 커넥터 토큰은 서명 데이터와 분리된 프로비저닝 정보지만, 설치 시 서명된 바인딩과 일치해야 합니다.
- 구형 비서명 `bundle.tunnel`, 다른 고객 호스트, 형식이 잘못된 토큰은 등록하지 않습니다.
- 로컬 cloudflared 설정이 현재 라이선스와 정확히 같을 때만 Named Tunnel을 시작합니다.
- Production의 Quick Tunnel은 기본 차단되며 `VO_ALLOW_QUICK_TUNNEL=1`은 제한된 임시 진단에만 사용합니다.

### 12.5 LiveKit 설치 보안과 외부망 설정

패키지에는 고정 LiveKit API key/secret이나 자격 증명이 든 런타임 YAML을 넣지 않습니다. 첫 실행 시 설치별 자격 증명을 생성합니다. 외부망 화면공유를 사용할 때는 고객 네트워크에 맞춰 다음 항목을 검토합니다.

```text
LIVEKIT_USE_EXTERNAL_IP=true
LIVEKIT_TURN_ENABLED=true
LIVEKIT_TURN_UDP_PORT=3478
# 필요 시 TURN TLS 도메인/포트/인증서/키 추가
```

Cloudflare Tunnel은 앱과 LiveKit 신호의 HTTPS/WSS를 연결합니다. 실제 미디어에는 UDP `50000~50200`, ICE/TCP `7881`, 또는 TURN 경로가 필요합니다. 방화벽 범위는 고객 보안 정책과 실제 런타임 설정에 맞춰 최소한으로 엽니다.

### 12.6 화면공유 권한·한도

- 고정 5건 제한은 제거되었습니다. 서명된 건물에서 화면공유가 활성화된 실제 스크린 수가 동시 송출 상한입니다.
- 한 방은 발표자 한 명이며, 같은 사용자의 중복 송출은 차단합니다.
- LiveKit 토큰은 고객·템플릿·방·역할에 맞게 발급하고 연결마다 고유 participant identity를 사용합니다.
- 정리 누락과 고아 발표자 상태를 서버가 정리하며, 녹화는 화면공유 주최자에게만 허용합니다.

### 12.7 관리자 외부망 진단 해석

`GET /api/admin/media-diagnostics`는 `server.monitor` 권한이 필요하며 다음을 점검합니다.

- LiveKit 제어 포트와 ICE/TCP 접근
- 서명된 미디어 호스트 DNS 및 HTTPS/WSS
- `use_external_ip`, TURN UDP/TLS 설정

이 결과가 정상이더라도 서버 단독으로 외부 UDP 통과를 확정할 수 없습니다. 외부 PC와 휴대폰 데이터망을 사용해 서로 다른 두 방의 동시 송출, 영상, PC 탭 오디오가 방별로 분리되는지 확인합니다.

### 12.8 현재 남은 작업

- 고객망별 TURN/TLS와 외부 ICE 호환성 실기 매트릭스
- 한 고객의 여러 병원/지점/건물 운영 모델과 관리 UI

- try 공용 계정의 동시 점유/TTL 제어

1. `npm run package:production` → `npm run verify:package:production` 순서로 실행한다(`.agent/package_build/SKILL.md`).
   - **빌드 전에 `git status`를 확인한다.** Windows 패키지는 작업 폴더의 파일을 그대로 쓰므로, 커밋하지 않은 변경이 릴리스에 섞인다.
   - 넣지 않을 변경은 `git stash push <파일>`로 잠시 치우고, 빌드 후 `git stash pop`으로 되돌린다.
   - Linux 묶음은 커밋된 내용으로 만들므로, 두 플랫폼을 같은 커밋 기준으로 맞춘다.
2. 공급자 포털 → 릴리스 → 버전·운영체제 **Windows**로 `VirtualOffice_Server_Setup_v{버전}_production.exe`를 업로드한다.
   - 50MB 조각으로 올라가므로 100MB가 넘어도 된다.
   - 릴리스 노트는 한글을 써도 된다.
3. **서명 후 게시**를 누른다. 같은 버전에 Linux 묶음이 이미 게시돼 있으면 **새 파일 서명 후 재게시**를 누른다.
4. 고객은 `https://worknexus.calamus.ai.kr/download`에 회사 이메일과 일회용 번호로 로그인해 내려받는다.

### 13.2 라이선스 등록 `signature_invalid` (1.0.3 이하, 1.0.4에서 해결)

- **증상**: 고객 서버 관리자 콘솔에서 라이선스를 등록하면 `signature_invalid`가 난다. 같은 파일을 서버에서 직접 검증하면 통과한다.
- **원인**: 서버가 요청 본문을 조각마다 문자열로 바꿔서, 조각 경계에 걸린 한글(3바이트)이 깨졌다(`server/index.js` `parseJsonBody`).
  - 같은 PC(localhost)에서는 조각이 커서 드물게만 생긴다.
  - 다른 PC에서 랜으로 큰 라이선스(약 120KB, 건물·방 이름 한글)를 보내면 거의 항상 생긴다.
- **해결**: 1.0.4로 업데이트한 뒤 **같은 라이선스 파일**로 다시 등록한다. 재발급은 필요 없다.
- 8.3절(Cloudflare 시크릿 bake 타이밍)과는 다른 원인이다. 발급 포털은 서명 직후 자체 검증을 하므로, 발급이 성공했는데 등록만 실패하면 이 문제다.
