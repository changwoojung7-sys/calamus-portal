## 2. P0 — 세 대의 설치 서버를 이용한 분산 부하발생기

### 2.1 목적

현재 자동시험은 단일 개발 PC 또는 로컬 시험 서버 중심이다. 앞으로는 다음 세 장비에 설치된 실제 WorkNexus 서버와 각 Cloudflare 전용 도메인을 대상으로 시험한다.

- Windows 게이밍 PC 서버
- Windows 노트북 서버
- Linux i3·8GB 서버

각 장비는 시험마다 `대상 서버`, `부하 발생기`, `실제 사용자 단말` 역할을 교대한다. 대상 서버와 부하 발생기를 분리해 서버 자원과 부하발생기 자원을 혼동하지 않는다.

### 2.2 구성

```text
분산 시험 컨트롤러
  ├─ 대상 A: https://<windows-server-domain>
  │            wss://<windows-media-domain>
  ├─ 대상 B: https://<notebook-server-domain>
  │            wss://<notebook-media-domain>
  └─ 대상 C: https://<linux-server-domain>
               wss://<linux-media-domain>

부하 워커 1 ─ Chrome/WebRTC 가상 참여자 N명
부하 워커 2 ─ Chrome/WebRTC 가상 참여자 N명
실제 단말  ─ 노트북·태블릿·휴대폰 육안/음성 확인
```

### 2.3 개발할 도구

#### 컨트롤러

- 시험 대상 도메인과 프로필을 선택한다.
- 여러 워커에 시작·중단·인원·역할·시험 시간을 전달한다.
- 워커 결과와 서버 상태를 하나의 실행 ID로 취합한다.
- JSON 원본, CSV 요약과 사람이 읽는 HTML 보고서를 생성한다.
- 한 번에 하나의 승인된 대상만 부하를 받도록 잠금을 둔다.

#### 워커

- Headless Chrome과 실제 `livekit-client`를 사용한다.
- 마이크·카메라·화면 영상·화면 오디오 합성 트랙을 발행한다.
- 회의실 입장·퇴장, 방 이동, 재입장, 화면공유 교체와 근처 대화를 반복한다.
- 타운홀은 발표자와 청중 역할을 분리한다.
- 연결, 트랙 구독, 실제 바이트 수신, 재연결, 정리 완료를 측정한다.
- Windows와 Linux에서 같은 명령으로 실행할 수 있게 Node.js CLI로 만든다.

#### 대상 서버의 시험 세션

운영 DB를 시험 계정으로 오염시키지 않도록 관리자만 생성할 수 있는 일회성 시험 세션을 설계한다.

- 기본값은 비활성화한다.
- 관리자 인증과 별도 `load-test` 권한이 있어야 한다.
- 실행 ID, 허용 인원, 대상 방, 만료시간을 서버가 서명한다.
- 시험 ID는 일반 사원·근태·조직도에 저장하지 않는다.
- 만료 또는 중단 시 WebSocket·LiveKit 참가자·공유 상태를 모두 정리한다.
- 모든 시작·중단·실패를 감사 로그에 남긴다.

### 2.4 안전장치

- 저장소에는 실제 도메인, 관리자 비밀번호, LiveKit secret과 터널 토큰을 기록하지 않는다.
- 로컬 비추적 설정 파일 또는 환경변수로만 대상 정보를 전달한다.
- 허용 도메인 목록 밖에는 실행하지 않는다.
- `--confirm-target <hostname>`을 입력하지 않으면 부하를 시작하지 않는다.
- 기본 최대 30명, 100명 이상은 별도 확인 옵션을 요구한다.
- 초당 입장 인원을 제한하는 ramp-up을 적용한다.
- 모든 워커를 즉시 종료하는 `stop` 명령과 서버 만료시간을 둔다.
- 일반 고객 운영시간에는 실행하지 않는다.

### 2.5 시험 프로필

| 프로필 | 주요 흐름 | 기본 규모 |
|---|---|---:|
| `meeting-cycle` | 방 이동→회의→마이크·카메라→화면·소리 공유→퇴장 | 30명 |
| `meeting-soak` | 위 흐름을 장시간 반복하고 누수·재연결 측정 | 30명·2~8시간 |
| `auditorium` | 실제 1080p 화면·소리 한 개를 다수 구독 | 100명 |
| `townhall` | 예약·입장·발표·손들기·게스트 재입장·종료 | 100/200명 |
| `movement` | 여러 층·방 이동과 범위 패킷 검증 | 100/300명 |
| `reconnect` | 네트워크 중단·서버 또는 LiveKit 재시작 후 회복 | 10/30명 |

### 2.6 완료 기준

- 세 서버를 설정 파일에서 선택해 동일 시험을 실행할 수 있다.
- 두 대 이상의 워커가 하나의 실행 ID로 분산 부하를 발생시킨다.
- 실제 앱·미디어 Cloudflare 도메인 경로를 이용한다.
- 시험 중단 후 참가자, 공유 상태와 LiveKit Room이 남지 않는다.
- 보고서에 서버 사양·도메인 별칭·시험 조건·성공률·p50/p95·CPU·메모리·대역폭이 기록된다.
- 도메인·토큰·이메일·비밀번호와 같은 비밀정보는 보고서에서 마스킹된다.

## 3. P0 — 혼합 단말 미디어 안정성 검증

### 3.1 30명 회의 장시간 시험

- 합성 참여자 26명과 실제 PC·태블릿·휴대폰 4명
- 2시간 이상 실행
- 5분마다 방 이동, 10분마다 회의 입장·퇴장
- 마이크·카메라 On/Off, 공유 시작·종료·재공유
- 근처 대화와 회의실 미디어를 반복 전환

합격 기준:

- 고아 참가자·고아 화면공유·다른 방 미디어 수신 0건
- 회의 입장 성공률 99% 이상, 최종 반복은 전원 성공
- 입장 완료 p95 10초 이내
- 네트워크 복구 p95 15초 이내
- 2시간 후 메모리·Room·트랙 수가 기준 범위로 복귀

### 3.2 실제 네트워크 장애 시험

- Wi-Fi 끄기·켜기
- Wi-Fi↔LTE/5G 전환
- 유선↔Wi-Fi 전환
- 모바일 화면 잠금·백그라운드 후 복귀
- Cloudflare connector 재시작
- LiveKit 재시작
- 앱 서버 재시작

각 단계에서 재연결 UI, 새 토큰 발급, 이전 Room 정리, 마이크·카메라·공유 상태와 방 격리를 검증한다.

### 3.3 iOS·Android 오디오 검증

- 마이크 Off 상태에서도 공유 소리 재생 버튼으로 음성을 들을 수 있어야 한다.
- Bluetooth 이어폰 연결·해제와 통화 오디오 경로 변경을 확인한다.
- 무음 스위치, 브라우저 자동재생 차단, 백그라운드 복귀를 구분해 안내한다.
- 실제 스피커·마이크 사용 시 에코와 공유 소리 재입력을 확인한다.

## 4. P0 — 자동 진단과 운영 가시성

### 4.1 사용자 진단

오류를 `연결 실패` 하나로 표시하지 않고 다음 단계로 나눈다.

- 앱 API 연결
- 로그인·세션
- LiveKit 토큰 발급
- WSS 시그널링
- ICE 후보와 선택 경로
- UDP·ICE/TCP·TURN
- 마이크·카메라 권한
- 브라우저 오디오 자동재생
- 발행·구독 트랙
- 네트워크 변경과 재연결

### 4.2 관리자 진단

- 현재 앱·DB·LiveKit·cloudflared 상태
- 방별 참가자, 발표자, 발행·구독 트랙 수
- 참가자별 RTT, jitter, packet loss와 선택된 ICE 유형
- 서버 CPU·메모리·네트워크 송수신
- 최근 토큰 발급·재연결·정리 실패
- 민감정보를 제거한 진단 ZIP 내려받기

### 4.3 완료 기준

- 고객이 오류 화면과 진단 파일만으로 어느 계층이 실패했는지 구분할 수 있다.
- 진단 파일에 비밀번호, JWT, LiveKit secret과 터널 토큰이 포함되지 않는다.
- 관리자가 방별 고아 참가자와 화면공유를 확인하고 안전하게 정리할 수 있다.

## 5. P1 — 기업용 인증·권한·감사

### 5.1 인증 기반 정리

1. 현재 로그인·세션·토큰 저장·로그아웃 경로 위협 모델 작성
2. 관리자 MFA(TOTP)와 복구코드
3. 범용 OIDC 로그인 기반
4. Microsoft Entra ID 연결
5. 폐쇄망 Active Directory/LDAPS 연결

`Active Directory`는 사내 직원 계정 장부이고, `LDAP/LDAPS`는 그 장부를 조회하는 규칙이다. `Microsoft Entra ID`는 Microsoft 365에서 사용하는 클라우드 계정 체계다. 인터넷 사용 기업에는 OIDC/Entra ID를, 폐쇄망 기업에는 AD/LDAPS 또는 고객 사내 IdP를 우선 검토한다.

### 5.2 권한 세분화

- 시스템 관리자
- 인사·조직 관리자
- 방·시설 관리자
- 회의·타운홀 운영자
- 감사 조회자
- 일반 직원

각 API가 화면 표시와 관계없이 서버에서 권한을 검증하도록 자동시험을 추가한다.

### 5.3 감사 로그

- 로그인 성공·실패·잠금
- 사용자·조직·권한 변경
- 회의·타운홀 생성·수정·삭제
- 화면공유·녹화 시작·종료
- 백업·복원
- 라이선스·도메인·터널 설정
- 감사 로그 조회와 내보내기

위변조 탐지, 보존기간, CSV·Syslog 내보내기와 개인정보 마스킹 정책을 함께 설계한다.

### 5.4 공급망·비밀정보

- Windows와 Linux 산출물의 SBOM 생성
- 의존성 취약점 점검과 조치 기준
- 릴리스·라이선스 서명키 분리 유지
- LiveKit secret·터널 토큰·백업 파일 암호화 저장 검토
- 보안 업데이트 지원기간과 긴급 패치 절차 문서화

## 6. P1 — 모바일·저사양 사용성

## 7. P1 — 사원·조직·일정·근태 연동

### 7.1 CSV 정기 동기화

- 변하지 않는 사번을 기준키로 사용한다.
- 신규·수정·휴직·퇴사를 구분한다.
- 사원을 물리 삭제하지 않고 비활성화한다.
- 적용 전 변경 예정 목록과 오류를 미리 보여 준다.
- 관리자 승인 또는 예약 실행을 지원한다.
- 비밀번호는 CSV로 받지 않는다.
- 처리 결과를 감사 로그에 남긴다.

### 7.2 일정

1. Google Calendar
2. Microsoft 365 Calendar
3. 표준 ICS 가져오기·구독
4. 고객별 그룹웨어 API 어댑터

그룹웨어는 고객마다 다르므로 공통 일정 모델과 어댑터 규격부터 만든다. 개별 제품 연동은 계약형 추가 개발로 둔다.

### 7.3 근태 데이터 제공

- 읽기 전용 API
- 기간·사번·부서 범위
- 페이지네이션과 재시도 안전성
- API 키 또는 OAuth 클라이언트 권한
- 호출 IP·주체·기간 감사 로그
- API를 사용할 수 없는 고객을 위한 CSV 유지

### 7.4 NAS·문서관리

기본 제품 범위에서 제외한다. 고객이 가상 오피스 안에서 문서까지 통합하려는 명확한 요구를 제시한 경우에만 고객 보안팀 검토 후 별도 연동으로 판단한다.

## 8. P1 — 백업·장애복구·고가용성

### 8.1 백업 보강

- 백업 성공·실패 알림
- 백업 파일 암호화와 키 복구 절차
- 고객이 지정한 암호화 외장 저장소 또는 접근통제된 원격 저장소로 2차 복제
- 보관기간과 용량 경보
- 월 1회 자동 또는 반자동 시험 복원
- 복원 결과와 DB 무결성 보고서

### 8.2 장비 장애

- 동일 장비 복구와 새 장비 교체 절차를 UI에서 구분한다.
- 새 장비는 라이선스 재발급이 필요함을 복원 전에 안내한다.
- 서버 교체 후 도메인·터널·LiveKit·DB·업로드 파일 검증을 자동화한다.

### 8.3 고가용성

초기 일반 상품은 단일 서버를 유지한다. 대기업·핵심업무 고객을 위해 별도 엔터프라이즈 구조를 설계한다.

- 앱 서버 장애 감지와 재기동
- LiveKit 장애 감지와 회의 재입장
- DB 복제 또는 외부 DB 전환 가능성
- 대기 서버와 DNS·터널 전환
- RPO·RTO 등급과 지원 범위

자동 전환을 구현하기 전에는 `고가용성`을 마케팅 문구로 사용하지 않는다.

## 9. P1 — 공식 성능 사양

### 9.1 서버 등급별 시험

| 등급 | 시험 장비 | 목표 |
|---|---|---|
| 저사양 시험 | Linux i3·8GB | 설치 가능 범위와 안전 동시접속 한계 탐색 |
| 일반 권장 | 4코어 8스레드·8GB 이상 | 30명 회의와 100명 이하 일반 접속 |
| 대규모 권장 | 8코어 16스레드·16GB 이상 | 200~300명 공간 접속과 다중 회의 |
| 강당·타운홀 | 12~16코어·32GB·1~2.5Gbps | 100명 강당·200명 타운홀 |

권장 사양은 분산 부하발생기로 다시 측정한 뒤 확정한다. 저사양 i3 서버 결과를 대규모 지원 근거로 사용하지 않는다.

### 9.2 반드시 기록할 값

- 서버 CPU 모델·논리 코어·메모리·OS
- 유선·무선·인터넷 회선과 링크 속도
- 앱과 미디어 도메인 경로
- 전체 접속자와 방별 참가자
- 마이크·카메라·화면공유·공유 오디오 수
- 해상도·프레임·코덱·비트레이트
- 연결 성공률, 입장 p50/p95, 재연결 시간
- CPU p50/p95/최대, 메모리 최대와 시험 후 복귀량
- 네트워크 송수신, RTT, jitter, packet loss, TURN 비율
- 모바일 배터리와 발열

### 9.3 공개 원칙

- `자체 합성 부하 시험`, `혼합 실제 단말 시험`, `고객 파일럿 시험`을 구분한다.
- 인원만 표시하지 않고 시험 장비·미디어 조건·지속시간을 함께 표시한다.
- 실패 단계도 삭제하지 않고 원인과 안전 권장값을 기록한다.
- 고객 납품 전에는 고객 서버·회선에서 설치 완료 검수를 다시 수행한다.

다음 증빙이 준비된 기능만 홈페이지와 제안서의 확정 사양으로 사용한다.

## 12. 개발 순서

### 1단계

1. 분산 부하발생기 컨트롤러·워커·보고서
2. 일회성 부하시험 세션과 안전장치
3. 세 서버 순환 시험과 30명 혼합 단말 장시간 시험
4. 사용자·관리자 미디어 자동 진단

### 2단계

1. 인증·권한 위협 모델
2. 관리자 MFA와 역할 세분화
3. 감사 로그·Syslog
4. OIDC/Entra ID
5. 모바일 2D 경량 모드

### 3단계

1. CSV 조직 정기 동기화
2. Google·Microsoft 일정 연동
3. 근태 읽기 전용 API
4. 백업 암호화·알림·시험 복원
5. 설치 완료 자동 검수 보고서

### 4단계

1. 폐쇄망 AD/LDAPS
2. 대기업용 고가용성 구조
3. 고객별 그룹웨어 어댑터
4. 실제 파일럿 결과 기반 권장 사양 확정

## 13. 즉시 다음 작업

첫 개발 작업은 **분산 부하발생기의 설정 형식, 워커 통신, 일회성 시험 세션과 보고서 스키마 구현**이다.
