## 📌 [영업 및 경영진 검토용] 3분 세일즈 브리핑 & 2-Track 아키텍처

워크넥서스(WorkNexus)는 기업의 보안 정책과 네트워크 환경에 맞춰 **두 가지 배포 모델(2-Track)**을 표준 제공합니다. 영업 단계에서 고객사 보안팀과 미팅 시 아래 비교표를 통해 3분 안에 명확한 설득이 가능합니다.

### 1. 2-Track 배포 모델 및 단일 패키지 원칙

워크넥서스는 제품의 파편화를 방지하기 위해 **설치 패키지를 OS별 단 2종으로 고정**하며, **네트워크 모드(클라우드형 vs 폐쇄망형)는 고객사 관리자 콘솔에서 원클릭 토글(ON/OFF)**로 자율 제어합니다.

* **배포 패키지 (단 2종):**
  1. **Windows용 올인원 패키지 (`.zip`)**: 일반 PC 및 Windows Server 지원 (내장 Node.js, SQLite, LiveKit)
  2. **Linux VM용 엔터프라이즈 패키지 (`.tar.gz`)**: 사내 클라우드 및 가상화 VM 지원 (Docker Compose / Systemd)
* **라이선스 기본 정책:**
  * 모든 라이선스에는 공급사가 **고객 전용 고정 도메인(`회사약칭.calamus.ai.kr`, Cloudflare 터널)을 기본 발급**합니다.
  * **폐쇄망 운영 시**: 관리자 센터 → **외부 접속 및 터널 설정**에서 **외부 터널 차단(폐쇄망 전환)**을 누르면(Linux는 설치 때 `--no-tunnel`) 터널이 멈추고 서버는 외부로 연결하지 않습니다. 사내 DNS·사내 CA로만 접속합니다.
  * **외부 접속 허용 시**: 같은 화면에서 **외부 터널 켜기**를 누르면 고정 도메인이 다시 열립니다. 라이선스 재발급은 필요 없습니다. 이때 웹 화면·로그인·채팅 같은 웹 요청은 Cloudflare 터널을 거칩니다(DB와 음성·영상 미디어는 거치지 않음).
  * **외부 VPN 사용 여부**: 폐쇄망 운영 시 외부 접속을 사내 VPN(SSL-VPN)으로 허용할지, 사내 PC에서만 쓰게 할지는 고객사 보안 정책에 따라 정합니다.

| 비교 항목 | Track 1: 표준 클라우드형 (Standard) | Track 2: 고보안 폐쇄망형 (Enterprise Zero-Trust) |
| :--- | :--- | :--- |
| **적용 고객** | 일반 기업, 스타트업, 신속 도입 희망사 | **금융권, 공공기관, 방산, 대기업, 망분리 사업장** |
| **외부 통신** | 웹·신호(HTTPS·WSS)는 Cloudflare 터널 경유(포트포워딩 불필요). DB·미디어는 사내 | **서버의 외부 연결 없음 (터널 OFF)** |
| **터널 제어** | 관리자 콘솔에서 **[터널 ON]** | 관리자 콘솔에서 **[터널 OFF]** (언제든 전환 가능) |
| **서버 환경** | 사내 일반 PC / 미니PC / 클라우드 VM | **고객사 자체 프라이빗 클라우드 VPC / 사내 온프레미스 VM** |
| **도메인 / SSL** | Cloudflare 관리 공인 도메인 및 자동 SSL | **사내 전용 FQDN (`.local`, `.corp`) + 사내 CA(사설 인증서)** |
| **외부/재택 접속** | 공인 브라우저 주소 직접 접속 | **고객사 표준 VPN(SSL-VPN / IPsec) 접속 여부 자율 결정** |
| **공급사 원격접속** | 없음 (고객 서버에 원격 접속하지 않음) | **없음 (고객사 보안팀 자체 운영)** |

### 2. 보안팀 설득 3대 핵심 팩트 (Sales Key Pitch)
1. **“DB와 음성·영상 미디어는 고객 서버에만”**  
   사원 명부, 근태 기록, 채팅, 화이트보드, 게시판은 고객 서버의 DB에만 저장되고, 화상회의·화면공유 미디어는 고객 서버의 LiveKit이 중계합니다(저장 안 함). 단, 고정 도메인(터널)을 켜 두면 **웹 접속 경로(로그인·채팅 등 웹 요청)는 Cloudflare를 거칩니다.** 이 구분을 보안팀에 정확히 설명합니다.
2. **“폐쇄망 모드에서는 서버의 외부 연결 없음”**  
   라이선스에 고정 도메인이 들어 있어도 관리자가 터널을 끄면 터널 프로세스가 기동되지 않습니다. 라이선스는 파일로 오프라인 검증합니다. 웹 화면의 글꼴도 앱에 내장되어 있어 사용자 PC가 인터넷 글꼴 서버에 접속하지 않습니다.
3. **“사내 사설 PKI(AD CS 등 내부 인증서) 수용”**  
   사내 CA 인증서를 신뢰하는 PC에서는 브라우저의 HTTPS 요구 조건을 충족해, 보안 경고 없이 화면공유·카메라·마이크를 사용할 수 있습니다.

### 1-2. VM 환경에서의 하드웨어 라이선스 바인딩 원리
> [!NOTE]  
> **Q. 실물 PC 메인보드가 아닌 가상 머신(VM)에서도 라이선스 발급이 정상 작동하나요?**  
> **A. 네, 정상 작동합니다.**  
> 워크넥서스 서버는 VM 환경을 자동 감지하여 하이퍼바이저가 고유하게 부여하는 **System UUID**와 **OS Machine-ID**를 수집합니다.

- **Windows VM**: `Get-CimInstance Win32_ComputerSystemProduct`의 `.UUID` (VMware/Azure/AWS 고유 가상 UUID)
- **Linux VM**: `/sys/class/dmi/id/product_uuid` 및 systemd의 `/etc/machine-id`
- 생성된 발급요청서(`license-request.json`)에는 해당 VM의 고유 SHA-256 해시가 담기고, 발급된 라이선스는 전자서명으로 위·변조 여부를 검증합니다.

### 1-3. 서버 권장 하드웨어 사양 (2026-09-30 부하시험 기준)

제품 한도: 동시접속 **50 / 100 / 200 / 300명**(계약 선택, 사원 + 외부 참석자(타운홀·방 회의)), 등록 사원 수 제한 없음, 방별 회의 **일반 방 30명 · 강당 100명**(고객 관리자가 방마다 1~100명으로 조정), 타운홀 **200명**(1080p VP9 송출, 약 1.7 Mbps/인 → 200명 약 370 Mbps).

| 거래처 유형 | 사용 형태 | CPU | RAM | SSD | 네트워크 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **일반 (소규모)** | 동시 100명 이하, 30명 이하 방 회의 | 4코어 8스레드 | 8 GB | 100 GB | 1 Gbps 유선 |
| **일반** | 동시 300명 이하, 30명 이하 방 회의 여러 개 | 8코어 16스레드 | 16 GB | 200 GB | 1 Gbps 유선 |
| **강당·타운홀** | 위 + 100명 강당 발표 또는 타운홀 | 12~16코어 | 32 GB | 300 GB | **2.5 Gbps 유선 권장** (최소 1 Gbps 전용) |

* **서버는 반드시 유선**으로 연결합니다. 무선(Wi-Fi)이나 100 Mbps 포트에서는 강당·타운홀 송출이 불가능합니다.
* 산정 근거(시험 PC: 6코어 노트북, 서버·미디어·시청자 동시 실행):
  * 강당 100명에게 1080p 발표 화면 송출: 서버 송신 약 **300 Mbps**, 미디어 서버 CPU 약 **3.6코어**.
  * 동시접속 300명 중 100명이 동시에 이동: 웹서버 CPU 약 0.7코어, 이동 지연 p95 약 60 ms.
  * 30명 회의(마이크 29개, 카메라, 화면공유) 10회 반복 정상.
* 발표 화면은 **회의 창이나 미리보기를 연 사람에게만** 전송됩니다(3D 스크린만 바라보는 사람은 받지 않음). 강당·타운홀 행사 중에는 다른 대형 회의를 동시에 열지 않는 것을 권장합니다. 강당 100명과 타운홀이 동시에 1080p로 송출되면 1 Gbps 회선이 거의 가득 찹니다.
* Windows용 미디어 서버는 과부하 시 스스로 부하를 줄이지 못하므로, 위 사양보다 CPU·회선 여유를 두는 것이 안전합니다.

## 📝 3. 상세 단계별 구축 절차

### 1단계. 접속 이름(FQDN) 2개 정하기
웹 브라우저의 WebRTC 보안 표준에 따라 **웹 애플리케이션용 도메인**과 **LiveKit 미디어 제어용 도메인** 총 2개가 필요합니다.
- **앱 접속 주소**: `vo.company.local` (또는 `office.company.co.kr`)
- **미디어 신호 주소**: `vo-rtc.company.local` (또는 `office-rtc.company.co.kr`)

> [!TIP]
> 사내 전용 도메인(`.local`, `.corp`, `.internal`)은 사내 CA 인증서만 사용 가능합니다.  
> 만약 회사가 소유한 공인 도메인(`vo.company.co.kr`)으로 사내 DNS를 구성하면 사내 CA뿐 아니라 상용 공인 인증서도 적용 가능합니다.

### 2단계. 사내 DNS에 이름 등록 (A 레코드)
사내 DNS 서버에 두 개의 이름을 서버 IP(예: `192.168.0.50`)로 등록합니다. 외부 인터넷에는 일체 공개되지 않습니다.

#### Windows AD DNS 서버 (PowerShell 기준)
```powershell
# 1. 회사 도메인 영역이 이미 있는 경우 (스플릿 DNS)
Add-DnsServerResourceRecordA -ZoneName "company.local" -Name "vo"     -IPv4Address "192.168.0.50"
Add-DnsServerResourceRecordA -ZoneName "company.local" -Name "vo-rtc" -IPv4Address "192.168.0.50"

# 2. 독립 전용 영역으로 등록하는 경우
Add-DnsServerPrimaryZone -Name "vo.company.local" -ReplicationScope "Domain"
Add-DnsServerResourceRecordA -ZoneName "vo.company.local" -Name "@" -IPv4Address "192.168.0.50"
Add-DnsServerPrimaryZone -Name "vo-rtc.company.local" -ReplicationScope "Domain"
Add-DnsServerResourceRecordA -ZoneName "vo-rtc.company.local" -Name "@" -IPv4Address "192.168.0.50"
```

#### Linux BIND DNS 서버 기준
```text
vo.company.local.     IN  A  192.168.0.50
vo-rtc.company.local. IN  A  192.168.0.50
```

#### DNS 검증 (사내 PC 및 VPN 연결 PC에서 실행)
```bash
# Windows
Resolve-DnsName vo.company.local
Resolve-DnsName vo-rtc.company.local

# Linux/Mac
nslookup vo.company.local
```
두 주소 모두 서버 VM의 사내 IP(`192.168.0.50`)가 정상 반환되어야 합니다.

### 3단계. 사내 CA(사설 인증서) 발급
회사 사내 인증기관(Active Directory Certificate Services 등)에서 인증서를 발급합니다.

1. **주체 대체 이름(SAN, Subject Alternative Name)**에 반드시 두 이름을 모두 등록합니다:
   - `DNS Name = vo.company.local`
   - `DNS Name = vo-rtc.company.local`
2. **용도**: 서버 인증 (Server Authentication, OID `1.3.6.1.5.5.7.3.1`)
3. **개인키 내보내기**: PFX 형식 또는 PEM 형식(`cert.pem`, `key.pem`)
4. **루트 인증서 확인**: 사내 임직원 PC의 "신뢰할 수 있는 루트 인증 기관"에 회사 루트 CA 인증서가 설치(GPO 자동 배포)되어 있는지 확인합니다.

> [!IMPORTANT]
> PEM 형식 변환이 필요한 경우:
> ```bash
> openssl pkcs12 -in vo_cert.pfx -clcerts -nokeys -out cert.pem
> openssl pkcs12 -in vo_cert.pfx -nocerts -nodes -out key.pem
> ```

### 4단계. HTTPS 리버스 프록시 구성 (Windows / Linux)

프록시 서버가 443 포트로 TLS 암호화를 처리한 후, 사내 서버 내부의 앱(3001)과 미디어 신호(7880)로 전달합니다.

#### 방법 A: Windows Server 환경 (Caddy 초간편 구성)
1. Caddy 실행 파일(`caddy.exe`)을 `C:\caddy\`에 배치합니다.
2. 인증서 파일(`cert.pem`, `key.pem`)을 `C:\caddy\certs\`에 복사합니다.
3. `C:\caddy\Caddyfile`을 생성합니다:
   ```text
   vo.company.local {
       tls C:/caddy/certs/cert.pem C:/caddy/certs/key.pem
       reverse_proxy 127.0.0.1:3001
   }

   vo-rtc.company.local {
       tls C:/caddy/certs/cert.pem C:/caddy/certs/key.pem
       reverse_proxy 127.0.0.1:7880
   }
   ```
4. 실행 및 서비스 등록:
   ```powershell
   cd C:\caddy
   .\caddy.exe validate
   .\caddy.exe run
   ```

#### 방법 B: Linux / Docker 환경 (Nginx 구성)
Nginx 가상 호스트 설정 파일(`/etc/nginx/conf.d/workverse.conf`):
```nginx
# 1. 앱 웹/API/WebSocket (vo.company.local)
server {
    listen 443 ssl http2;
    server_name vo.company.local;

    ssl_certificate     /etc/ssl/certs/cert.pem;
    ssl_certificate_key /etc/ssl/certs/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 3600s;
        proxy_buffering off;
    }
}

# 2. LiveKit SFU 미디어 제어 신호 (vo-rtc.company.local)
server {
    listen 443 ssl http2;
    server_name vo-rtc.company.local;

    ssl_certificate     /etc/ssl/certs/cert.pem;
    ssl_certificate_key /etc/ssl/certs/key.pem;

    location / {
        proxy_pass http://127.0.0.1:7880;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 3600s;
        proxy_buffering off;
    }
}
```

## 🛡️ 4. 방화벽 규칙 및 사내 VPN(SSL-VPN) 연동

### 4-1. 인바운드 방화벽 필수 포트

| 출발지 | 목적지 | 프로토콜 / 포트 | 필수 여부 | 용도 및 설명 |
| :--- | :--- | :--- | :---: | :--- |
| **사내망 & VPN 대역** | 프록시 | **TCP 443** | **필수** | 웹 브라우저 접속, 채팅 API, WSS 신호 |
| **사내망 & VPN 대역** | 서버 | **UDP 50000 ~ 50200** (Windows) / **50000 ~ 50300** (Linux 도커판) | **필수** | **실시간 화면공유·영상·음성 (WebRTC DTLS-SRTP)** |
| **사내망 & VPN 대역** | 서버 | **TCP 7881** | **예비** | 사내 보안 정책상 UDP 차단 시 TCP 백업 터널 |
| 프록시 (127.0.0.1) | 서버 내부 | TCP 3001, 7880 | 필수 | 프록시 내부 라우팅 (외부 차단) |
| **임직원 PC 대역** | 서버 | **TCP 3001, 7880** | **차단** | **보안 취약점 예방 (프록시 우회 직접 접속 차단)** |

> 미디어 UDP 범위는 설치판마다 다릅니다. Windows 설치판은 50000~50200, Linux 도커판은 50000~50300(`deploy/docker.env`의 `LIVEKIT_RTC_UDP_PORT_START/END`)입니다. 아래 예시는 Windows 기준입니다.

#### Windows 방화벽 PowerShell 예시
```powershell
# 1. 443 HTTPS 허용 (사내망 및 VPN 대역)
New-NetFirewallRule -DisplayName "WorkNexus HTTPS (443)" -Direction Inbound -Action Allow `
  -Protocol TCP -LocalPort 443 -RemoteAddress 192.168.0.0/16,10.0.0.0/8

# 2. 미디어 UDP 포트 허용
New-NetFirewallRule -DisplayName "WorkNexus Media UDP (50000-50200)" -Direction Inbound -Action Allow `
  -Protocol UDP -LocalPort 50000-50200 -RemoteAddress 192.168.0.0/16,10.0.0.0/8

# 3. 미디어 예비 TCP 허용
New-NetFirewallRule -DisplayName "WorkNexus Media TCP (7881)" -Direction Inbound -Action Allow `
  -Protocol TCP -LocalPort 7881 -RemoteAddress 192.168.0.0/16,10.0.0.0/8

# 4. 직접 포트(3001, 7880) 외부 차단 (로컬 프록시만 허용)
New-NetFirewallRule -DisplayName "WorkNexus Block Direct Internal Ports" -Direction Inbound -Action Block `
  -Protocol TCP -LocalPort 3001,7880
```

### 4-2. 사내 VPN(SSL-VPN / IPsec) 연계 핵심 체크리스트
재택근무자나 외근자가 회사 VPN을 통해 워크넥서스에 접속할 때 점검할 2가지 핵심 포인트입니다.

1. **VPN DNS Name Server 지정**:
   - VPN 클라이언트가 연결되었을 때, 회사 사내 DNS(`192.168.x.x`)를 우선 조회하도록 VPN 터널 프로파일에 사내 DNS IP를 명시해야 합니다. (도메인 `vo.company.local`이 정상 해석되어야 함)
2. **분할 터널링(Split-Tunneling) 시 라우팅 테이블 및 UDP 정책**:
   - 워크넥서스 서버 IP(`192.168.0.50/32`)가 VPN 터널 라우팅 경로에 포함되어 있어야 합니다.
   - VPN 게이트웨이에서 **UDP 50000~50200 패킷**을 Drop(차단)하지 않고 통과시키는지 확인합니다. (차단 시 TCP 7881로 자동 폴백되나 음질/화질 지연이 발생할 수 있음)

## ✅ 5. 최종 검증 체크리스트

모든 설정을 마친 후 서로 다른 네트워크 대역(사내 유선 PC, 사내 Wi-Fi PC, VPN 접속 PC)에서 검증을 수행합니다.

### 연결 및 보안 검증
- [ ] 브라우저 주소창에 `https://vo.company.local` 입력 시 주소창에 안전한 자물쇠 표시 및 인증서 경고 없음
- [ ] 인증서 정보 확인 시 발급 대상 SAN에 `vo.company.local`과 `vo-rtc.company.local`이 모두 명시되어 있음
- [ ] `http://192.168.0.50:3001` 또는 `http://192.168.0.50:7880` 직접 접속 시 방화벽에 의해 접속 차단됨

### 미디어 및 협업 기능 검증
- [ ] 회의실(Room) 입장 후 화상회의 카메라/마이크 켜기 시 상대방과 정상 양방향 송수신
- [ ] 100석 대강당(타운홀) 입장 및 연단 화면공유 시 1080p 고화질 정상 스트리밍
- [ ] 거리 기반 근거리 대화(Spatial Audio) 아바타 접근 시 음성 송수신 확인
- [ ] 브라우저 개발자 도구(F12) 콘솔(Console)에 `Mixed Content` 또는 `insecure WebSocket` 경고 없음

## ❓ 6. 문제 해결 및 보안팀 단골 FAQ

### Q1. 사내 CA 인증서로 교체했는데 브라우저에서 '인증서 신뢰할 수 없음' 경고가 뜹니다.
- **원인**: 해당 클라이언트 PC에 회사의 사내 루트 CA 인증서가 설치되어 있지 않습니다.
- **조치**: AD 그룹 정책(GPO)으로 "신뢰할 수 있는 루트 인증 기관"에 회사 루트 인증서를 배포하거나, 테스트 PC의 인증서 관리자(`certmgr.msc`)에 루트 CA를 수동 등록하세요.

### Q2. 화면공유 시작 시 "room connection has timed out" 오류가 발생합니다.
- **원인**: `vo-rtc.company.local` 미디어 신호 도메인의 리버스 프록시 전달이 실패했거나, 인증서 SAN에 `vo-rtc`가 누락된 경우입니다.
- **조치**: 브라우저에서 `https://vo-rtc.company.local`을 직접 열어 인증서 오류가 없는지 확인하고, 프록시 설정의 7880 포트 WebSocket 전달 여부를 확인하세요.

### Q3. 음성과 영상이 10초 뒤에 끊기거나 매우 끊깁니다.
- **원인**: 사내 방화벽 또는 VPN 게이트웨이에서 **UDP 50000~50200 포트**를 차단하여 고품질 WebRTC 대신 TCP 백업 터널(7881)로 지연 수신되고 있는 상태입니다.
- **조치**: 방화벽 장비 및 사내 L3 스위치에서 워크넥서스 서버를 향한 UDP 50000~50200 포트를 인바운드 허용하세요.

### Q4. 라이선스를 갱신할 때도 서버 재시작이 필요한가요?
- **답변**: 재시작이 필요 없습니다. 관리자 콘솔 웹 화면(`tab=license`)에서 발급받은 라이선스 파일(`.lic`)을 업로드하면 무중단(Zero-Downtime)으로 즉시 적용됩니다.
