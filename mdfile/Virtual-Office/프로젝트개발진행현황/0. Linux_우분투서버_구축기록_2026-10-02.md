## 1. 서버 기본 점검 (2026-10-02)

### 1.1 접속 방식

- 원격 관리 화면: Cockpit (`https://서버주소:9090`, `sudo apt install -y cockpit`)
- 명령 실행: SSH(22). 개발 노트북에서는 Node.js `ssh2` 라이브러리로 `.env`의 계정 정보를 읽어 접속했다(비밀번호는 화면·로그에 남기지 않음).
- 사람이 직접 작업할 때는 VS Code의 **Remote-SSH** 확장으로 서버 폴더·터미널을 열 수 있다(SSH 키 로그인 권장).

### 1.5 1단계 결론

- 설치는 가능하다. 다만 CPU·메모리가 운영 권장 사양보다 낮고 다른 서비스가 메모리를 쓰고 있어, **기능 시험용**으로 본다(수십 명 이상 부하 시험에는 부적합).
- ufw가 꺼져 있어 의도와 달리 모든 포트가 열려 있다. 방화벽을 켤 때는 SSH(22)·Cockpit(9090)을 **먼저 허용**한 뒤 켜야 원격 접속이 끊기지 않는다.
- Docker는 ufw 규칙을 우회해 컨테이너 포트를 연다. 방화벽 정책은 Docker 설치 후 함께 정한다.

## 2. Docker 설치 (2026-10-02)

### 2.1 설치 명령 (Docker 공식 저장소)

Ubuntu 기본 `docker.io` 대신 Docker 공식 저장소의 `docker-ce`를 쓴다(최신 버전·Compose 플러그인 포함). 설치 전 충돌 패키지(`docker.io`, `podman-docker`, `containerd`, `runc`)가 없는 것을 확인했다.

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
. /etc/os-release
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $VERSION_CODENAME stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker $USER      # 다시 로그인하면 sudo 없이 docker 사용
sudo systemctl enable --now docker
docker run --rm hello-world         # 동작 확인
```

### 2.2 결과

| 항목 | 결과 |
|---|---|
| Docker | 29.8.2 (서비스 active, 부팅 시 자동 시작) |
| Docker Compose | v5.5.1 |
| 시험 컨테이너 | `hello-world` 정상 |
| Docker 기본 네트워크 | `docker0` 172.17.0.0/16 (MicroK8s calico 10.1.x와 겹치지 않음) |
| iptables FORWARD 기본 정책 | ACCEPT 유지 |

### 2.3 기존 서비스 영향 확인

- Wekan(8080)·Nextcloud(80)·Cockpit·SSH 모두 정상(HTTP 200).
- MicroK8s: Docker 설치 순간 네트워크 규칙이 다시 적용되면서 `calico-node`가 한 번 재시작됐고(준비 중 `readiness probe failed`는 정상), 약 1분 뒤 `1/1 Running`으로 복구됐다. 파드 DNS 조회 정상.
- 설치 후 `needrestart`가 NetworkManager·gdm 등 일부 서비스 재시작을 "보류"로 표시했다. 새 라이브러리는 다음 재부팅 때 반영되며 지금 동작에는 영향이 없다.

### 2.4 남은 확인

- 방화벽(ufw)은 아직 켜지 않았다. Docker는 ufw 규칙을 우회해 컨테이너 포트를 공개하므로, WorkNexus 설치 후 필요한 포트를 정리해 함께 정한다(SSH 22·Cockpit 9090을 먼저 허용한 뒤 켤 것).

## 3. Dockerfile·Compose 수정 (2026-10-02)

실제 서버에서 빌드·기동하며 발견한 문제를 순서대로 고쳤다. 모두 `npm run verify:docker-config`가 다시 잡아내도록 검사를 추가했다.

| # | 증상 | 원인 | 수정 |
|---|---|---|---|
| 1 | (예상) 컨테이너 시작 시 `ERR_MODULE_NOT_FOUND` | Dockerfile이 서버 모듈을 이름으로 골라 복사하면서 `media-diagnostics.js`·`livekit-log-router.js`·`machine-fingerprint.js`와 `license-public.pem` 누락 | 모두 복사. 검사 스크립트가 `server/index.js`의 import 관계를 따라가 빠진 파일을 찾는다 |
| 2 | (예상) 인증요청파일 생성 실패 `machine_fingerprint_unavailable` | 컨테이너는 비루트(`node`)라 `/sys/class/dmi/id/*`를 못 읽고 자체 `/etc/machine-id`도 없음 | `docker-compose.yml`에 호스트 `/etc/machine-id`를 읽기 전용으로 연결 |
| 3 | 이미지 빌드 실패 `TS2307 Cannot find module '../../shared/building-template-engine.js'` | 웹 빌드 단계에 `shared/` 폴더를 복사하지 않음 | 웹 빌드 단계에 `COPY shared ./shared` |
| 4 | (예상) 사내망 PC의 화상·음성 연결 실패 | 컨테이너 LiveKit이 내부 IP(172.x)를 브라우저에 알려 줌 | `docker-compose.media.yml`에 `node_ip: ${LIVEKIT_NODE_IP}`, `docker.env`에 서버 사내망 IP |
| 5 | Redis 재시작 반복 `setpriv: setresuid failed: Operation not permitted` | Redis 이미지가 root→redis 사용자로 바꾸는데 `cap_drop: ALL`이 이를 막음 | Redis를 처음부터 `user: "999:999"`로 실행 |
| 6 | `verify:docker-config` 실패 | LiveKit 방 상한을 210으로 바꾼 뒤 검사가 100을 기대 | 검사 기대값 210으로 갱신 |

관련 커밋: `818deb8`, `94a4b5a`, `6b5ea07`, `f668588`.

## 4. 이미지 빌드·설치·기동 (2026-10-02)

### 4.1 소스 전달

서버에 GitHub 계정 정보를 두지 않기 위해 개발 노트북에서 **커밋된 소스 중 빌드에 필요한 경로만** 압축해 SSH(SFTP)로 보냈다(1.1MB, `.env`·라이선스·DB 미포함, 공개키만 포함).

```bash
# 개발 노트북(프로젝트 루트)
git archive --format=tar.gz -o worknexus-src.tar.gz HEAD \
  package.json package-lock.json tsconfig.json vite.config.ts index.html \
  scripts/viteCloudflareTunnelPlugin.ts src public product-policy.json server shared \
  docker-compose.yml docker-compose.media.yml deploy release-manifest.json .dockerignore

mkdir -p ~/worknexus/src && tar -xzf ~/worknexus/worknexus-src.tar.gz -C ~/worknexus/src
```

### 4.2 이미지 빌드

```bash
cd ~/worknexus/src
```

### 4.6 확인된 제약 (다음 단계에서 결정)

- **HTTPS 미구성**: `http://사내망IP:3001`에서는 브라우저 보안 정책상 마이크·카메라·화면공유가 동작하지 않는다(로그인·3D·채팅은 가능). 화상 기능 시험에는 사내 인증서 + 리버스 프록시(Nginx/Caddy) 또는 고정 도메인 터널이 필요하다.
- **Cloudflare 터널 미포함**: Windows 패키지는 `cloudflared.exe`를 함께 넣지만 Docker 이미지에는 `cloudflared`가 없어, 라이선스의 고정 도메인 터널이 자동으로 켜지지 않는다. 리눅스 판에서 외부 접속을 지원하려면 별도 `cloudflared` 컨테이너가 필요하다.
- **TURN 중계 포트**: LiveKit TURN이 30000~40000/udp 중계 범위를 쓰지만 Compose에 열려 있지 않다. 사내망 직접 연결에는 영향이 없고, 외부망·UDP 차단 환경에서만 문제가 된다.

## 5. 최초 관리자·라이선스 등록 (2026-10-02, 완료)

### 5.1 진행 순서

1. 브라우저에서 `http://<서버 IP>:3001` 접속 → 최초 시스템관리자 생성.
2. 관리자 콘솔 → 라이선스 탭 → 요청 파일(`calamus-4c2d5aac-….calamus-request`) 내려받기.
3. 공급자 포털 → 라이선스·서버에서 발급. 계약: ubuntu-Linux · office-300 · 2026-10-01~2026-11-01.
4. 관리자 콘솔에서 `.calamus-license` 등록.

### 5.2 겪은 문제와 해결

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| 1 | 포털 발급 시 `subdomain_slug_required` | 신규 거래처의 고정 주소 약칭이 비어 있었고, 입력 화면도 없었다 | 고객 메뉴에 약칭 입력란 추가(커밋 `2b4461c`). 약칭 입력 후 발급 성공(`LIC-20261001-D892B54D`) |
| 2 | 관리자 콘솔 등록 시 `signature_invalid` | 키 문제가 아니었다. 공개키는 저장소·서버 소스·컨테이너 세 곳 모두 같았고, 같은 파일을 컨테이너 안에서 직접 검증하면 통과했다. 서버가 요청 본문을 조각마다 문자열로 바꿔, 조각 경계에 걸린 한글이 깨졌다(라이선스 약 120KB, 랜 전송 시 조각이 작아짐) | `parseJsonBody()`가 Buffer를 모아 한 번에 변환하도록 수정(커밋 `738d26a`). 서버에 반영 후 이미지 재빌드·컨테이너 재생성 |

- 컨테이너를 다시 만든 뒤에도 설치 ID가 `4c2d5aac-1e5f-43ed-b492-efb038c95271`로 그대로였다(라이선스와 일치).
- 컨테이너 파일시스템은 읽기 전용(`read_only`)이라 `docker cp`가 거부된다. 점검용 파일은 `docker exec -i ... < 파일`처럼 표준입력으로 넘긴다.

## 7. 마무리 정리 (2026-10-02)

### 7.1 옛 설치 폴더 정리

- `install.sh` 뒤에도 redis·cloudflared 컨테이너는 설정이 같아 다시 만들어지지 않았고, 옛 폴더(`~/worknexus/src`)에 묶여 있었다. 그래서 `sudo /opt/worknexus/compose.sh up -d --no-build --force-recreate redis cloudflared`로 다시 만들었고, 이제 네 컨테이너 모두 `/opt/worknexus`에서 관리된다. 외부 주소는 계속 200 응답이다.
- 삭제: `~/worknexus/src`, `~/worknexus/build-1.0.4`, 소스 압축 파일, 점검용 `~/lic.json`.
- 보관: `~/worknexus/backups/pre-1.0.4-…`(1.0.3 시절 데이터·설정 백업), `~/worknexus/build.log`.

### 7.2 방화벽(ufw)

- 이 서버에는 MicroK8s(calico), Nextcloud, Wekan, Cockpit, 파일 공유 등 다른 서비스가 함께 돈다. ufw를 켜면 이 서비스들의 포트가 막힐 수 있다.
- Docker가 공개한 포트(3001·7880·7881·3478/udp·50000-50300/udp)는 Docker가 iptables에 직접 규칙을 넣어 **ufw 규칙을 거치지 않는다.** 그래서 ufw를 켜도 WorkNexus 포트는 걸러지지 않는다.
- 결론: 공용 시험 서버에서는 ufw를 켜지 않는다. 고객 서버에서 접근을 제한해야 하면 ufw가 아니라 다음 방법을 쓴다.
- **이후 사용자가 ufw를 켰다(2026-10-02).** 허용 규칙은 OpenSSH와 9090/tcp(Cockpit)뿐이다. 그래도 노트북(사내망)에서 3001·7880 모두 200, 고정 주소 200으로 응답했다. Docker 공개 포트가 ufw를 거치지 않는다는 것이 실제로 확인됐다. WorkNexus는 영향이 없고, ufw는 SSH 등 다른 서비스 보호용으로 동작한다.
  - 사내망 방화벽·공유기에서 막는다.
  - 또는 `deploy/docker.env`의 `VO_BIND_ADDRESS`를 사내 IP로 지정한다.

### 7.3 사외(외부)에서의 영상·음성 — 확인된 제약

- 고정 주소(HTTPS)로 **화면과 신호(WebSocket)는 사외에서도 접속된다.** 영상·음성 데이터(UDP)는 LiveKit이 알려 주는 서버 사내 IP(`LIVEKIT_NODE_IP`)로 직접 가야 하므로, 사외 PC는 연결되지 않는다. Cloudflare 터널은 이 UDP 미디어를 실어 나르지 못한다.
- 사외 영상까지 필요하면 고객 사내망에서 다음이 필요하다(서버 밖 네트워크 작업이라 이 시험 서버에서는 검증하지 못했다).
  - 공유기·방화벽에서 UDP 50000-50300, TCP 7881, UDP 3478을 서버로 포트포워딩한다.
  - `LIVEKIT_USE_EXTERNAL_IP=true`로 공인 IP를 알리게 한다.
  - LiveKit 내장 TURN의 중계 포트 범위(기본 30000-40000)는 현재 compose에 열려 있지 않다. 사외 지원을 정식으로 할 때 범위를 정해 함께 연다.
- 유료 클라우드 TURN은 쓰지 않는다(원칙: 클라우드 비용 0원).
