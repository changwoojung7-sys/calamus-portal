## 1. 기획 개요 및 목표

본 시스템은 분절되어 있던 `[병원 탐색] ➔ [1~3곳 비교] ➔ [상담 의뢰] ➔ [병원 회신] ➔ [비용/조건 비교]`의 전체 과정을 보호자와 요양기관 양측의 마찰(Friction) 없이 하나로 연결하는 핵심 서비스다.

### 핵심 목표
1. **보호자 이탈률 최소화**: 심리적 저항과 수기 작성 피로도를 없애기 위해 주관식 타이핑을 100% 배제하고, 원클릭 태그 칩과 점진적 정보 노출(단계 역순)을 제공한다.
2. **요양기관 회신율 극대화**: 복잡한 12개 비용 인풋 대신 **원클릭 표준 견적 패키지(프리셋 3종)**와 30초 퀵 서류 칩을 제공하여 30초 내 회신이 가능하도록 한다.
3. **챗봇-상담 완벽 연계**: 챗봇(`CareSearchChat`)에서 나눈 환자 조건이 상담 양식에 자동 체크되어 중복 입력 없이 즉시 접수되도록 한다.
4. **팩트 기반 투명한 비교**: 입원 가능 여부, 빠른 입원일, 항목별 비용 범위(공단부담/식대/간병비/비급여), 미확인 항목을 동일한 기준의 비교표로 제공한다.

### 2.2 기관회원 원클릭 답변 시스템 (`HospitalAdmissionResponseForm.tsx`)

요양병원 원무과 및 상담실무자가 30초 내에 회신할 수 있는 최적화 스튜디오를 제공한다.

1. **원클릭 표준 견적 패키지 (프리셋 3종)**:
   - `[⚡ 4인실+공동간병 표준형]` : 월 185~240만원 (공단부담 60~75만 + 식대 35~45만 + 간병비 90~120만)
   - `[⚡ 1~2인실 집중케어형]` : 월 355~510만원 (상급병실 차액 120~180만 + 1:1 집중간병)
   - `[⚡ 전문재활·투석 집중형]` : 월 255~350만원 (재활/투석 본인부담금 포함 패키지)
   - 클릭 한 번으로 공단부담, 식대, 간병비, 병실차액, 비급여 항목, 산정 기준, 포함/제외 항목이 즉각 자동 기입.
2. **30초 퀵 서류 칩 & 상용구 템플릿**:
   - 다빈도 요구 서류: `[+의사소견서]`, `[+투약기록지]`, `[+검사결과지]`, `[+코로나음성확인서]` 원클릭 토글.
    - 상황별 상용구는 병상 확보·즉시 입원을 단정하지 않고 `[현재 기준 상담 가능]`, `[서류 검토 후 확정]`, `[대기 가능 여부 확인]`처럼 최종 확인이 필요함을 명시.
   - 입원 가능일 퀵 날짜 버튼: `[오늘]`, `[내일]`, `[3일 뒤]`, `[1주일 뒤]`.
3. **보호자 의뢰서 스플릿 뷰**:
    - 화면 상단에 보호자가 선택한 환자 상태 요약 카드(입원 시기, 병실, 간병, 처치 필요 항목)를 직관적으로 제공하여 즉각적인 수용 판단 지원.
4. **거절 및 사실 확인 안전장치**:
   - `UNAVAILABLE` 답변은 견적 입력 화면과 저장 payload에서 제외하며, DB 트리거가 거절 대상 견적의 INSERT/UPDATE도 차단한다.
   - 수용 가능·조건부 답변은 담당자가 현재 병상·의료진·치료 제공·비용 정보를 실제 확인했다는 체크 후에만 제출할 수 있다.

## 3. 전원 상담 상태 모델 및 감사 이력 (기존 문서 통합)

### 3.1 상태 전이 다이어그램 (State Lifecycle)

```text
[요청 접수] PENDING
     │
     ▼ (병원 담당자 의뢰서 열람 시)
   VIEWED
     │
     ├─────────────────────┬──────────────────────┬─────────────────────┐
     ▼                     ▼                      ▼                     ▼
[상담 가능]             [추가정보 필요]         [조건부 검토 가능]      [현재 수용 어려움]
CONSULTABLE              NEEDS_INFO             ACCEPTABLE            DECLINED
(전화 상담 안내)        (추가 질문/서류 요청)    (견적 패키지 회신)      (정중한 사유 안내)
     │                     │                      │
     └─────────────────────┴──────────────────────┘
                           │
                           ▼ (양측 협의 완료 시)
                      CONFIRMED (최종 입원 확정)
```

- **상태 정의 원칙**:
  - `PENDING`: 보호자 요청 접수 완료, 병원 미열람 상태.
  - `VIEWED`: 병원 담당자가 보호자 의뢰 요약을 최초 열람한 시각 기록.
  - `ACCEPTABLE`: 전달된 조건 기준의 **조건부 검토 가능** 상태이며, 법적 입원 확정이 아님을 화면에 명시.
  - `NEEDS_INFO`: 추가 서류나 검사가 필요한 상태로, `transfer_consult_messages`를 통해 질문을 발송.
  - `DECLINED`: 병상 부재나 의료 인프라 불일치로 인한 정중한 거절 상태.
  - `CONFIRMED`: 전화 상담 및 서류 심사 완료 후 양측이 확정한 상태.
- **이력 불변 원칙**:
  - 운영상 잘못 선택한 상태는 이전 상태로 되돌릴 수 있으나, 변경 이력은 `transfer_consult_target_events`에 영구 보존된다.

### 3.2 데이터베이스 스키마 및 저장 원칙

```sql
-- 1. 상담 요청 마스터 (transfer_consult_requests)
CREATE TABLE transfer_consult_requests (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid REFERENCES auth.users(id),
  request_version text NOT NULL DEFAULT 'v2.0',
  patient_requirements jsonb NOT NULL,      -- 선택형 태그 칩 배열 및 환자 상태
  admission_preference jsonb NOT NULL,      -- 희망시기, 병실, 간병, 예산
  contact_info jsonb NOT NULL,              -- 보호자 연락처, 통화 가능 시간
  idempotency_key uuid NOT NULL UNIQUE,     -- 중복 접수 원천 방지
  created_at timestamptz DEFAULT now()
);

-- 2. 병원별 상담 대상 및 상태 (transfer_consult_targets)
CREATE TABLE transfer_consult_targets (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  request_id uuid REFERENCES transfer_consult_requests(id) ON DELETE CASCADE,
  hospital_id text NOT NULL,                -- 심평원 ykiho
  status text NOT NULL DEFAULT 'PENDING',   -- PENDING, VIEWED, ACCEPTABLE, NEEDS_INFO, DECLINED
  admission_review_status text,             -- UNREVIEWED, CONDITIONALLY_AVAILABLE 등
  bed_availability_status text,             -- AVAILABLE_NOW, WAITLIST 등
  earliest_admission_date date,
  estimated_wait_days integer,
  response_valid_until date,
  required_documents text[],                -- 퀵 서류 칩 목록
  hospital_response_text text,              -- 병원 회신 상용구/설명
  hospital_contact_phone text,              -- 회신 유선 전화
  viewed_at timestamptz,
  responded_at timestamptz,
  client_read_at timestamptz                -- 보호자 확인 시각 (새 답변 배지 계산)
);

-- 3. 상태 변경 감사 로그 (transfer_consult_target_events)
CREATE TABLE transfer_consult_target_events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  target_id uuid REFERENCES transfer_consult_targets(id) ON DELETE CASCADE,
  from_status text,
  to_status text NOT NULL,
  note text,
  changed_by uuid REFERENCES auth.users(id),
  created_at timestamptz DEFAULT now()
);

-- 4. 항목별 견적 버전 이력 (transfer_consult_quotes)
CREATE TABLE transfer_consult_quotes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  target_id uuid REFERENCES transfer_consult_targets(id) ON DELETE CASCADE,
  version integer NOT NULL DEFAULT 1,
  package_name text,                        -- '4인실+공동간병 표준형' 등
  covered_min integer, covered_max integer,
  meal_min integer, meal_max integer,
  caregiver_min integer, caregiver_max integer,
  room_surcharge_min integer, room_surcharge_max integer,
  noncovered_min integer, noncovered_max integer,
  total_monthly_min integer, total_monthly_max integer,
  included_items text[], excluded_items text[],
  valid_until date,
  created_at timestamptz DEFAULT now()
);
```

### 3.3 보호자·기관 권한 격리 (SECURITY DEFINER RPC)
- **보호자**: 본인이 작성한 요청과 선택한 병원의 회신 데이터만 조회 가능 (`get_my_admission_consult_comparison`).
- **요양기관**: 승인된 `hospital_memberships`의 `ykiho`와 일치하는 대상 의뢰서만 조회 및 회신 가능 (`respond_admission_consult`).
- **PII 격리**: 보호자 연락처와 환자 상태는 외부 AI 프롬프트에 절대 전송되지 않으며 오직 선택된 병원의 승인된 담당자에게만 제한 제공된다.

### 4.1 대화 상태 모델 및 맥락 자동완성

```text

   │

   │
   ├─ 다빈도 케어 키워드 해석 (치매/인지, 욕창치료, 암요양, 투석, 재활)

   │
   ├─ 비교함 담기 ("첫 번째랑 세 번째 병원 상담받아볼래")
```

## 6. 알림 및 확정 이메일 설계 (기존 문서 통합)

### 6.1 인앱 실시간 알림
- 홈페이지 상단, 개인 설정, 상급병원 전원 탭에 **새 답변 배지 (`Badge`)** 노출.
- 병원의 `responded_at` 시각이 보호자의 `client_read_at` 시각보다 최신이면 읽지 않은 새 답변으로 자동 계산.

### 6.2 이메일 Outbox 큐 및 중복 방지 (향후 확장)
1. **발송 트리거**: 병원이 `ACCEPTABLE` 견적을 회신하거나, 양측 협의를 통해 `CONFIRMED`로 전환 시 발송 대기열(`outbox`)에 적재.
2. **보안 원칙**: 이메일 본문에는 환자의 상세 병력이나 민감정보를 담지 않으며, 안전한 확인을 위한 로그인 딥링크만 제공.
3. **중복 차단**: 이벤트별 `idempotency_key`를 적용하여 네트워크 재시도 시에도 단일 메일만 발송.
