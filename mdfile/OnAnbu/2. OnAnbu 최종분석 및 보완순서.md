## 2026-10-11 현행 실행계획 — “더 많은 병원”보다 “더 나은 결정”

> **2026-10-15 의료광고 안전 원칙:** 병원 간 우열·순위·점수·나란히 비교 기능은 제공하지 않는다. 검색 결과는 사용자가 선택한 조건을 충족하는 기관을 중립적으로 나열하고, 각 기관의 확인 사실·출처·미확인 항목을 독립적으로 보여준다. 여러 기관에 같은 상담을 보내는 기능은 `상담 요청 기관 선택`이며 답변도 기관별로 분리한다.

### 1. 현재 위치와 1단계 완료 기준

- 서울·경기 **병원급 이상** 기관은 공식 홈페이지를 확보했고, 현재 홈페이지 원문에 근거해 수집 키워드를 승인·거절하는 단계다.
- 이 작업은 단순 태그 등록이 아니라, 사용자가 결과를 믿을 수 있게 만드는 첫 번째 데이터 품질 관문이다. 크롤러가 수집한 값은 승인 전까지 검색 근거로 노출하지 않는다.
- 현 단계의 종료 기준은 “많이 승인했다”가 아니라 다음을 모두 만족하는 것이다.
  1. 대상 기관의 수집 후보가 승인·거절·재확인 필요 중 하나로 모두 분류되어 있다.
  2. 승인 태그마다 홈페이지 원문·URL·확인일이 남아 있고, 분리 대상 키워드나 진료과/의료진 프로필 오탐이 남아 있지 않다.
  3. URL 접속 불가·폐업·기관 불일치 사례는 검색 근거와 수집 데이터를 함께 정리한다.
  4. 7개 테마와 주요 필터별로 “근거 있는 기관 수 / 아직 확인되지 않은 영역”을 확인할 수 있다.

### 2. 키워드 승인 직후의 우선순위

| 우선순위 | 해야 할 일 | 사용자에게 생기는 가치 | 완료 판단 |
| --- | --- | --- | --- |
| P0 | 서울·경기 병원급 이상 키워드 승인 마감과 근거 누락 정리 | 검색 결과가 추측이 아니라 확인된 정보가 된다 | 위 1단계 종료 기준 충족 |
| P1 | 검색 결과를 **기관별 조건 확인 화면**으로 연결 | 내 조건에서 각 기관에 확인된 사실과 미확인 항목을 개별적으로 살펴본다 | 기관별 필수 조건 근거, 출처, 확인일, 확인 필요 항목 표시 |
| P1 | 결과 없음/조건 부족 시 대안 안내 | 빈 결과에서 이탈하지 않고 인접 지역·유사 조건으로 다음 행동을 한다 | 주요 테마·지역 조합의 빈 결과 흐름 점검 |
| P1 | 전화·상담 전 확인 질문 자동 정리 | “입원 가능합니까?”를 넘어 병상, 진료 가능 범위, 비용, 대기 등 정확히 묻는다 | 필터와 기관 정보에서 질문 목록 생성 |
| P2 | 확인일·출처·미확인 항목을 카드와 상세에 명확히 표시 | 최신성의 한계까지 알고 판단한다 | 핵심 사실마다 출처/확인일/재확인 필요 상태 노출 |
| P2 | 상담 요청 후 진행 상태와 기관 응답 기준 정비 | 요청을 보낸 뒤에도 다음 행동을 알 수 있다 | 접수·열람·응답 상태 및 기관 측 처리 기준 제공 |
| P3 | 수요·공백 기반으로 지역과 기관 유형을 확장 | 무작정 크롤링하지 않고 필요한 곳부터 넓힌다 | 테마×지역×기관유형 커버리지 표에 따라 다음 수집 대상 선정 |

### 3. 서울·경기 병원급 이상 다음의 데이터 확장 순서

1. **승인 데이터의 사용성 검증**: 먼저 서울·경기 병원급 이상에서 테마별 검색 결과, 0건 결과, 오탐 신고, 상담 전환을 본다. 데이터가 있어도 사용자가 원하는 기관을 못 찾으면 확장을 서두르지 않는다.
2. **공백 지도 작성**: `테마 × 시도 × 병원유형 × 주요 필터`별 승인 근거 기관 수, 마지막 확인일, 0건 검색 수를 집계한다. 이 표가 다음 크롤링과 수동 검수의 우선순위가 된다.
3. **병원급 이상 전국 확장**: 공백이 큰 테마·지역부터 공식 홈페이지 확보 → 수집 → 원문 근거 승인 순서로 진행한다. 병원급 이상은 입원 상담 수요와 확인할 의료 조건이 많아 먼저 유지한다.
4. **의원급 확장**: 모든 의원을 동일하게 넓히지 않고, 병원급 결과가 부족한 지역·소아/재활/정신건강 등 실제 검색 수요가 높은 조합부터 한다. 의원급은 입원 가능 여부와 역할이 다르므로 별도 안내를 유지한다.
5. **상시 신선도 루프**: 접속 실패 URL, 만료된 확인일, 사용자 신고, 기관의 직접 수정 요청을 별도 대기열로 만들고 재수집·재승인한다. 자동 수집은 후보 생성까지만, 공개 근거는 승인 절차를 유지한다.

### 4. 사용자가 OnAnbu를 이용해야 하는 이유

OnAnbu의 목표는 병원 목록이나 AI 답변을 하나 더 만드는 것이 아니다. 보호자가 막연한 상황을 **확인 가능한 조건**, **기관별 검증 사실**, **바로 할 수 있는 연락 행동**으로 바꾸게 돕는 것이다.

| 사용자의 문제 | OnAnbu가 제공해야 할 답 | 화면·기능 보완 방향 |
| --- | --- | --- |
| “어디가 우리 상황에 맞는지 모르겠다” | 내 필수 조건과 선호 조건에 맞는 기관, 그리고 맞지 않거나 미확인인 이유 | 결과 카드에 조건 일치 근거와 미확인 항목을 함께 표시 |
| “검색 결과를 믿어도 되는지 모르겠다” | 홈페이지·공공 데이터·기관 입력 중 무엇에 근거했는지와 확인일 | 출처 배지, 원문 근거, 마지막 확인일, 재확인 안내를 일관되게 제공 |
| “후보가 여러 개인데 무엇을 확인해야 할지 모르겠다” | 각 기관에서 확인된 사실과 직접 문의할 항목 | 기관별 확인 카드, 상담 요청 기관 선택, 보호자용 개별 공유 링크 |
| “전화해서 무엇을 물어봐야 하나” | 내 선택 조건에서 빠질 수 없는 질문과 준비 정보 | 기관별 전화·상담 체크리스트와 문의 내용 복사 기능 |
| “문의 후 어떻게 됐는지 모르겠다” | 요청 상태, 다음 해야 할 일, 기관 응답 여부 | 상담 타임라인과 알림. 실제 병상·비용 확정은 기관 확인이 필요하다고 명시 |

#### 사용자 가치에 직접 연결되는 제품 보완 제안

1. **‘이 기관에서 확인된 정보’ 요약**: AI 점수나 상대평가 없이 “선택 조건 3개 확인 / 2개는 전화 확인 필요”처럼 해당 기관의 근거와 한계를 보여준다.
2. **확인 후 행동 설계**: 기관 상세에서 상담 요청 기관 선택 또는 전화 체크리스트로 이어지게 한다. 여러 기관을 선택해도 나란히 비교하거나 우열을 요약하지 않는다.
3. **불확실성의 정직한 표현**: 병상, 입원 가능 여부, 비용, 대기 기간은 실시간 확정 정보처럼 보이지 않게 하고, 확인 주체와 확인 방법을 표시한다. 후기 없는 평점이나 임의의 기본 점수는 표시하지 않는다.
4. **보호자 맥락 보존**: 로그인 사용자에게는 최근 조건·상담 요청 기관·상담 상태를 저장해 다시 설명하는 부담을 줄인다. 민감 정보는 최소 수집·명확한 보관 목적·삭제 경로를 전제로 한다.
5. **기관이 정보를 최신으로 유지할 유인**: 기관회원에게는 자기 기관의 미확인 정보, 마지막 확인일, 상담 요청 현황을 보여주고 직접 정정·근거 제출 경로를 제공한다. 이것이 사용자 경험과 기관회원 가치가 만나는 지점이다.

### 5. 공개 확장 전에 갖춰야 할 운영·기술 기반

- **품질 관측**: 승인/거절 사유, URL 실패율, 오래된 태그 수, 테마별 0건 검색, 상담 전환·응답 시간을 운영 지표로 본다.
- **모바일 실기기 점검**: 검색 조건, 기관별 정보 확인, 상담 요청, 팝업 닫기, 긴 기관명·필터 줄바꿈을 실제 iOS/Android 브라우저에서 반복 검증한다.
- **성능 측정과 개선**: 검색 응답 시간, Supabase 쿼리 시간, 첫 화면 로딩, 번들 크기를 먼저 계측한 뒤 인덱스·쿼리·코드 분할을 적용한다. 데이터가 늘어난 뒤에만 파티셔닝을 검토한다.
- **변경 안전성**: 키워드 사전·DB 마이그레이션·크롤러 배포는 검증 SQL, 롤백 경로, 변경 이력을 한 묶음으로 관리한다.

### 6. 지금은 미루는 일

- 테마·필터를 더 많이 추가하는 작업, 근거가 부족한 AI 종합점수 고도화, 자동 승인, 후기·평점 확장, 네이티브 앱 출시, 광고·유료화 화면 확장은 우선순위가 아니다.
- 이들은 `근거 데이터 → 기관별 확인 → 상담/확인 → 최신성 관리` 흐름이 안정된 뒤에만 검토한다. 특히 자동화는 거절 사유가 충분히 축적된 필드부터 보조적으로 도입한다.

### 7. 다음 실행 백로그

1. 서울·경기 병원급 이상 키워드 승인 대기열을 근거·거절 사유까지 포함해 마감한다.
2. 테마·지역·기관유형별 승인 커버리지와 0건 검색을 보는 운영 대시보드를 만든다.
3. 검색 결과의 ‘기관별 조건 일치 근거 / 미확인 항목’을 정리하고, 최대 3곳에 같은 문의를 보낼 수 있는 `상담 요청 기관 선택` 흐름을 운영한다. 기관 간 비교표·순위·점수는 만들지 않는다.
4. 상담·전화 체크리스트와 상담 상태 화면을 사용자 흐름에 연결한다.
5. URL·확인일·사용자 신고 기반의 재검수 대기열을 운영하고, 그 결과로 전국 병원급 이상 확장 순서를 결정한다.

**판단 원칙:** 다음 기능은 “더 많은 정보를 보여주는가”가 아니라 “보호자가 더 빠르고 안전하게 다음 결정을 내릴 수 있는가”로 우선순위를 정한다.

- **크롤링**: 검토 대기열(승인 태그만 검색 근거, 180일 만료), 병원별 일괄 승인·승인 취소, 민감 태그 엄격 규칙, 크롤러 화면·야간 배치 1,000곳 제한 해제, `--skip-recent-days`, 로컬 사본 폐기, 다른 PC용 관리자 로그인 크롤러 EXE(서비스 키 미포함).
- **테스트**: `npm run test:themes`(제품 코드 직접 호출·ROLLBACK DB 흐름), `test:themes:live`, `test:sensitive-keywords`, `test:category-codes`.

### 오전 반영

- 당시 산부인과·모자보건을 포함한 6대 테마를 검색, 전원상담 저장, 기관/보호자 상태 카드까지 연결했다. 이후 호스피스를 독립 테마로 추가해 현재는 7대다.
- 전원 테마가 RPC에서 유실되던 문제를 전용 컬럼·두 JSON 동기화 RPC와 CHECK 제약으로 보완했다.
- 기관회원 산부인과·소아정신 인프라 4종 입력과 AI 서버 필터 근거를 연결했다.
- 기관의 수용 어려움은 5개 사유 중 하나를 클릭하도록 하고 DB에서도 상태 모순을 차단했다.
- 타 PC 배치는 ASCII 전용 런처로 교체했고, 실제 원인이던 EXE 카탈로그 로더 오류를 수정한 뒤 `/api/health` 응답까지 검증했다.

## 3. 권장 실행 순서

### 1단계 — 법적 고지·약관 전문 실제화 (P0) [✅ 완료]
- **전문 열람 모달 구현 (`TermsModal.tsx`)**: 서비스 이용약관, 개인정보 처리방침 전문 탭 열람 모달 구현.
- **가입 화면 연동 (`AuthModal.tsx`)**: 가입 폼 내 '전문보기' 버튼 연동 및 `v1.0` 동의 이력 매핑.
- **법적 고지 명시**: 수집 항목/목적/보유기간, 비용 계산 예상치 고지, AI 비의료적 보조 고지 반영.

### 2단계 — 보호자 마찰 없는 상담 & 요양기관 원클릭 답변 시스템 (P0) [✅ 완료]
- **보호자 이탈 방지 3단계 상담 (`AdmissionRequestWizard.tsx`)**: 주관식 타이핑을 100% 배제하고 다빈도 환자 상태를 선택형 태그 칩으로 전환.
- **점진적 정보 노출 (단계 역순)**: 1단계 환경/선호 ➔ 2단계 테마별 환자 상태 ➔ 3단계 안심 연락처. 통계 근거 없는 고정 회신시간 대신 기관 운영 상황에 따라 달라진다는 안내를 제공한다.
- **챗봇 맥락 자동완성**: `CareSearchChat.tsx`에서 대화한 조건이 상담 마법사에 자동 체크되어 진입.
- **기관회원 원클릭 견적 패키지 (`HospitalAdmissionResponseForm.tsx`)**: 표준 견적 프리셋 3종, 퀵 서류 칩, 상용구 템플릿, 보호자 의뢰 요약 스플릿 뷰 지원.

### 3단계 — 호스피스 완화의료 3대 서비스 종합 체계 (P0) [✅ 완료]
- **공식 데이터 매칭**: 전국 127개 호스피스 전문기관의 심평원 `ykiho` 100% 매칭.
- **3대 서비스 & 인프라 규격화**: 입원형, 가정형, 자문형, 인가병상수, 간병보조인력(건보적용), 지정일자, 대상질환.
- **기관회원 상세정보 테이블(`hospital_provider_profiles`) 영구 격리**: 공공데이터 갱신 시 덮어쓰기 방지.
- **UI/UX 통합**: 다중 필터 연동 호스피스 세부 선택 칩 바, 호스피스 전용 3대 카드 시각화, 3단계 네비게이터 연동.

### 4단계 — AI 문지기 캐시 게이트 및 정밀 팩트 그라운딩 (P0) [✅ 완료]
- **자체 문지기 알고리즘 (`intentClassifier.ts`)**: 0원, 0.05초 고속 의도 추출 및 캐시 지식 즉각 반환.
- **가상/유령 병원 차단**: 대표 유선전화 미확인 병원 하드 필터링 (`selectUniqueMatch`).
- **하이브리드 프리미엄**: 비회원 1회 무료 체험 후 2회째 로그인 모달 유도.
- **인지 부하 해소**: B2C 종합 AI 적합도(`CareFit Score`) 단일 배지 및 추천 이유 아코디언 토글.

### 5단계 — 비공개 문의 및 사이트 활동 카운터 (P0) [✅ 완료]
- **비공개 문의게시판 (`support_inquiries`)**: 일반/기관회원 문의 작성, bcrypt 해시 인증 및 5회 잠금, 관리자 답변 RPC.
- **실시간 사이트 활동 카운터**: 오늘 방문자, 검색 실행, 병원카드 조회, 입원상담 요청 합계 표시.

### 6단계 — 공개 전 최종 브라우저·실기기 통합 회귀 검증 (P0) [진행 대상]
1. 비회원, 일반 개인회원, 승인 전 기관회원, 승인 기관회원, 시스템 관리자 계정 준비.
2. 모바일 실기기(iOS/Android) 및 PC 브라우저에서 가입 ➔ 로그인 ➔ 탐색 ➔ 전원상담 ➔ 기관답변 ➔ 로그아웃 흐름 수동 검증.
3. 병원찾기 다중 필터(투석/재활/ICU/호스피스/암요양/척추관절)와 지도 마커, 40개 추가 노출 검증.
4. 상급병원 기준 반경 검색, 3개씩 더보기, 전원설계 3단계 작성 및 1~3곳 전송 확인.
5. 기관회원 대시보드에서 보호자 의뢰서 스플릿 뷰 확인 및 원클릭 표준 견적 패키지 회신 검증.
6. 비용 시뮬레이터 시행일/출처/저장 동의/삭제 동작 검증.

**완료 기준**: 자동 테스트 전부 통과 + 브라우저/실기기 수동 체크리스트 전부 통과.

### 7단계 — AI Consensus 운영화 (P1)
- OpenAI / Gemini / Perplexity 공급자 키 관리, 비용 한도, timeout, 안전한 폴백 정책 운영 문서화.
- 다중 모델 배치 실행 주기와 실패 알림 연결.
- 모델별 단순 나열이 아닌 심평원 HIRA 팩트가 일치하는 추천 사유 정밀 병합.

### 8단계 — Trust / LUVIS 크롤러 운영 안정화 (P1)
- `official_website_trust_batch` 실패 원인을 DNS/TLS/timeout/robots/도메인 불일치 등으로 정밀 분류.
- 병원당 마지막 검증 결과, 실패 원인, 다음 재시도 일정, 근거 URL을 관리자 화면에 직관적으로 시각화.
- 공식 홈페이지 부재 시 무조건 0점이 아닌 "검증 URL 미확인"으로 격리 분류.

### 9단계 — 데이터 품질 및 후기 신뢰 운영 (P1/P2)
- HIRA 공공데이터 정기 갱신 주기 확립 및 기관 입력 정보와의 출처/일자 명확한 구분 표기.
- 후기(Review) 등록 시 실제 입원/진료 사실 검수 절차 및 악성/허위 광고 후기 대응 가이드라인 수립.

### 10단계 — 수익화 모델 및 모바일 앱 확장 (P3)
- 자연 검색 및 AI 정밀추천의 순위를 왜곡하지 않는 투명한 B2B 스폰서십/광고 영역 분리.
- `advertisement_products`, `campaigns`, `subscriptions`, `payments` 신규 도메인 설계.
- 모바일 앱(iOS/Android) 출시를 위한 REST/GraphQL API 규격화 및 푸시 알림 인프라 정의.

## 4. 하지 말아야 할 것 (Core Anti-Patterns)

- **AI 환각 정보 노출 금지**: 확인되지 않은 시설 정보나 폐업 기관을 AI 답변만으로 추가하거나 HIRA 팩트를 덮어쓰지 않는다.
- **Trust/AEO 점수의 의료 품질 오인 금지**: 웹사이트 가시성 및 AI 접근성 점수를 환자 치료 품질 점수로 호도하지 않는다.
- **원시 개인식별정보(PII) 유출 금지**: 환자 이름, 연락처, 상세 병력 원문을 외부 AI 프롬프트나 전원 상담 대상 외 외부에 전송하지 않는다.
- **광고 기반 순위 왜곡 금지**: 광고비를 납부한 기관이라도 필수 의료조건(투석, 재활, ICU, 호스피스 등)과 거리/팩트 기준보다 우선 정렬하지 않는다.
- **운영 DB 직접 수정 금지**: 마이그레이션 파일 기록 없이 운영 DB 스키마나 RPC 함수를 임의 수정하지 않는다.
